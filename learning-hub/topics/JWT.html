    Anatomy and claims

    A JWT (RFC 7519) is a set of claims serialized as JSON and protected by a signature. The compact form is three base64url strings joined by dots: header.payload.signature. That is technically a JWS (RFC 7515). An encrypted JWE (RFC 7516) has five segments and hides the payload; you rarely need one between your own services, and many APIs reject them outright.

    The single most important fact: base64url is encoding, not encryption. Anyone holding the token can read every claim. The signature only proves who issued it and that nobody changed it. So no passwords, no BSN or IBAN, nothing you would not print in a log line.

    How the signature is made

    signingInput = base64url(headerJson) + "." + base64url(payloadJson)
signature    = RSASSA-PKCS1-v1_5-SIGN( SHA-256(signingInput), issuerPrivateKey )   // RS256
token        = signingInput + "." + base64url(signature)

// verification on your API
valid = RSASSA-PKCS1-v1_5-VERIFY( SHA-256(signingInput), signature, publicKeyFromJWKS[kid] )

    Note that the signature covers the encoded bytes. Re-serializing the JSON with different whitespace or key order produces a different signing input, which is why you must never "decode, modify, re-encode" a token you intend to keep valid.

    Signing algorithms

    The real choice is symmetric versus asymmetric. With HMAC, the secret that verifies a token can also mint one, so every verifier is also a potential forger. With RSA or EC, the IdP keeps the private key and everyone else gets the public half from a JWKS endpoint. For anything with more than one service, use asymmetric.

    algTypeKeyUse it when
    HS256HMAC, symmetricShared secret, at least 256 random bitsIssuer and verifier are the same service. Short secrets are brute-forced offline.
    RS256RSA PKCS#1 v1.5RSA 2048+The default of almost every IdP. Widest support.
    PS256RSA-PSSRSA 2048+Same keys, more modern padding; required by some financial-grade profiles (FAPI).
    ES256ECDSA P-256EC keySmall tokens and fast signing. Don't hand-roll it; signature encoding and nonce generation are easy to get wrong.
    EdDSAEd25519OKP keyFast and misuse-resistant, but check every consumer supports it.
    noneUnsigned—Never. Reject at the allowlist.

    JWKS and key rotation

    An issuer publishes its public keys at a JWKS URL (discoverable from {issuer}/.well-known/openid-configuration as jwks_uri). Each key carries a kid. Your API caches the set and picks the key whose kid matches the token header. Rotation that never breaks anything follows one order:

    1. Publish the new public key in the JWKS next to the old one.
    2. Wait longer than your consumers' JWKS cache lifetime.
    3. Start signing with the new private key.
    4. Keep the old public key until the longest-lived token signed with it has expired, then remove it.

  "keys": [
    { "kty": "RSA", "kid": "acme-2026-10", "use": "sig", "alg": "RS256", "n": "u1cK…", "e": "AQAB" },

    End-to-end architecture

    One picture of where a token is born, where it travels and who checks it. The numbered path is a user signing into a web app and placing an order; ⑩ and ⑪ are a batch job calling the same API with its own identity.

    Client Service Security / auth Key store Cache Synchronous call Redirect, async or optional

    What each hop is responsible for

    The identity provider

    Authenticates people and clients, decides what goes into the token, signs it, publishes public keys, and handles refresh, revocation and logout. You configure it; you don't write it.

    The client or BFF

    Runs the login flow, stores tokens safely, attaches Authorization: Bearer, refreshes before expiry. It treats the access token as an opaque string and never makes authorization decisions from it.

    The gateway

    Rejects garbage early: signature, expiry, issuer, maybe a scope per route. It forwards the original token. It must strip any inbound identity headers like X-User-Id so callers can't forge them.

    Each resource server

    Validates the token again (zero trust: the network is not proof), checks aud, maps scopes and roles, and does object-level checks such as "does this sub own order 42?".

    Flows by scenario

    Five flows cover almost every backend system. Pick one to see the message sequence; dashed arrows are responses or redirects, loops are local work.

    Use for any human login: SPAs, server-rendered apps, mobile. The implicit flow and the password grant are deprecated in OAuth 2.1; Authorization Code with PKCE replaces both. PKCE ties the code to the client instance that started the flow, so an intercepted code is useless without the code_verifier.

    Why a BFF. Here the browser never sees a token; it holds a session cookie and the backend-for-frontend calls APIs with the access token. A pure SPA can run the same flow itself, but then tokens live in JavaScript, where any XSS can read them.

    Watch for: redirect_uri must match the registration exactly (scheme, host, port, path); state stops login CSRF; nonce stops ID token replay; ask for an API scope or audience or you'll get a token your API can't accept.

    Use for schedulers, batch jobs, consumers of a queue, any process acting as itself rather than as a user. The token's sub is the client ID, there is no refresh token, and you simply request a new token when the cached one is close to expiry.

    Client authentication options, weakest to strongest: client_secret_basic, private_key_jwt (the client signs a short JWT assertion with its own key, so no shared secret exists), and mutual TLS. On Kubernetes, workload identity federation can replace secrets entirely.

    Watch for: fetching a fresh token per request (it hammers the IdP and adds latency; cache it), and granting machine clients broad scopes "to make it work".

    Short access tokens, long refresh tokens. Access tokens can't be recalled once issued, so they live 5–15 minutes. The refresh token is only ever sent to the IdP, which can revoke it, and that is where long sessions come from.

    Rotation with reuse detection: each refresh returns a new refresh token and invalidates the old one. If an old one shows up again, either the client or an attacker has a copy, and the IdP can't tell which, so it revokes the whole family and forces a fresh login.

    Watch for: parallel requests that all hit 401 and all refresh with the same token. With rotation on, the second refresh looks like reuse and logs the user out. Make refresh single-flight: one in-progress refresh, everyone else awaits its result.

    The problem: Orders API received a token whose aud is orders-api, and now needs to call Payments API on the user's behalf. Forwarding the same token ("token relay") either fails Payments' audience check or, worse, means Payments accepts tokens meant for someone else.

    Token exchange (RFC 8693) asks the IdP for a new token for the new audience, keeping the user as sub and recording Orders as the actor in act. Microsoft Entra calls this pattern On-Behalf-Of and implements it with the jwt-bearer grant; Keycloak supports standard token exchange.

    Alternatives: if Payments doesn't care about the user, Orders can use its own client-credentials token instead. Inside a service mesh, mTLS proves which service is calling, while the JWT still carries which user it's for.

    The stateless trade-off: a JWT stays valid until exp no matter what happens at the IdP. Logout revokes the refresh token and ends the SSO session, but any access token already out there keeps working until it expires.

    Your options, cheapest first: short access-token lifetimes; revoke refresh tokens on logout, password change and account disable; a jti denylist with TTL equal to the token's remaining lifetime for high-risk cases; or token introspection (RFC 7662) on sensitive endpoints, which trades statelessness for an IdP call per request.

    Watch for: back-channel logout (the IdP calls each client's logout endpoint with a signed logout token) only works if your clients implement and expose that endpoint.

    How an API validates a token

    Order matters: cheap structural checks first, crypto next, claims after the signature is proven (an unsigned claim is just user input). In Spring Security, steps 1–8 happen inside BearerTokenAuthenticationFilter → JwtAuthenticationProvider → NimbusJwtDecoder.

    1. Extract the bearer tokenFrom Authorization: Bearer … only. Spring's DefaultBearerTokenResolver ignores query parameters unless you opt in, because URLs end up in logs.401 · no token → WWW-Authenticate: Bearer
    2. ParseThree segments, valid base64url, valid JSON. An opaque token fails here.Malformed token / Invalid JWT serialization
    3. Check the algorithm against your allowlistConfigured on the server, e.g. only RS256. Stops alg:none and RS→HS confusion.Another algorithm expected
    4. Select the key by kidFrom the cached JWKS of the configured issuer. Unknown kid triggers one rate-limited refetch, which is how rotation is picked up.no matching key(s) found
    5. Verify the signatureNow the claims can be trusted as the issuer wrote them.Invalid signature
    6. Check timeexp and nbf with clock skew. Spring's JwtTimestampValidator allows 60 s by default.Jwt expired at … / Jwt used before …
    7. Check the issuerExact match. JwtIssuerValidator, added automatically when you configure issuer-uri.The iss claim is not valid
    8. Check the audienceNot on by default. Add it, or any token from the same IdP for any other API gets in.The aud claim is not valid
    9. Check the token is the right kindReject ID tokens and refresh tokens used as access tokens: typ: at+jwt, Cognito's token_use, or the presence of a scope claim.
    10. Map authoritiesJwtAuthenticationConverter turns claims into GrantedAuthoritys and puts a JwtAuthenticationToken in the SecurityContext.
    11. Authorize the requestRoute rules (hasAuthority("SCOPE_orders.write")), method rules (@PreAuthorize), then object-level checks in your service. Broken object-level authorization is the number one API vulnerability on the OWASP API list, and no token can fix it for you.403 Forbidden · insufficient_scope
    12. Optional: revocationDenylist lookup by jti, or introspection, for endpoints where minutes of exposure after logout are not acceptable.

    SecurityConfig.java
    @Configuration
@EnableWebSecurity
@EnableMethodSecurity
class SecurityConfig {

  @Bean
  SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())            // stateless, bearer only, no cookies
        .cors(Customizer.withDefaults())         // lets OPTIONS preflight through
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/actuator/health/**").permitAll()
            .requestMatchers(HttpMethod.POST, "/orders/**").hasAuthority("SCOPE_orders.write")
            .requestMatchers("/admin/**").hasRole("ADMIN")      // needs ROLE_ADMIN
            .anyRequest().authenticated())
        .oauth2ResourceServer(rs -> rs.jwt(jwt -> jwt
            .jwtAuthenticationConverter(new KeycloakAuthConverter())))
        .build();
  }

  @Bean
  JwtDecoder jwtDecoder(@Value("${spring.security.oauth2.resourceserver.jwt.issuer-uri}") String issuer) {
    NimbusJwtDecoder decoder = (NimbusJwtDecoder) JwtDecoders.fromIssuerLocation(issuer);

    OAuth2TokenValidator<Jwt> audience = new JwtClaimValidator<List<String>>(
        JwtClaimNames.AUD, aud -> aud != null && aud.contains("orders-api"));

    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
        new JwtTimestampValidator(Duration.ofSeconds(30)),   // tighter than the 60 s default
        new JwtIssuerValidator(issuer),
        audience));
    return decoder;
  }
}

    Declaring your own JwtDecoder bean replaces Boot's auto-configured one, including the audiences and jws-algorithms properties, so restate everything you need in code.

    KeycloakAuthConverter.java — roles from nested claims
    class KeycloakAuthConverter implements Converter<Jwt, AbstractAuthenticationToken> {

  private final JwtGrantedAuthoritiesConverter scopes = new JwtGrantedAuthoritiesConverter(); // scope/scp → SCOPE_x

  @Override
  public AbstractAuthenticationToken convert(Jwt jwt) {
    Set<GrantedAuthority> authorities = new HashSet<>(scopes.convert(jwt));

    Map<String, Object> realmAccess = jwt.getClaimAsMap("realm_access");
    if (realmAccess != null && realmAccess.get("roles") instanceof Collection<?> roles) {
      roles.forEach(r -> authorities.add(new SimpleGrantedAuthority("ROLE_" + r)));
    }
    return new JwtAuthenticationToken(jwt, authorities, jwt.getClaimAsString("preferred_username"));
  }
}

    JWT or opaque access tokens

    A JWT is validated locally: no network call, scales freely, but can't be revoked before exp and exposes its claims to whoever holds it. An opaque token is a random reference that the API sends to the IdP's introspection endpoint (RFC 7662): instantly revocable and private, at the cost of one call per request (usually cached for seconds). A common split is opaque at the internet edge, exchanged by the gateway for an internal JWT ("phantom token" pattern).

    Issues and fixes

    First move for any 401: decode the token (header and payload) and read Spring's log at DEBUG. The WWW-Authenticate response header also carries the reason, e.g. error="invalid_token", error_description="Jwt expired at …".

    Signed JWT rejected: Another algorithm expected, or no matching key(s) foundEvery request gets 401, token looks finekey / alg
    Cause

    The token's kid isn't in the JWKS you're reading, or its alg isn't in your allowlist. Typical reasons: decoder pointed at the wrong realm or tenant; a token from another environment (test token against prod); a Microsoft Graph token sent to your API; the IdP signs with ES256 while you only allow RS256.

    Fix

    Compare the header's kid and alg with the keys at your jwks_uri. Point the decoder at the issuer that minted the token, request a token for your API's scope, or add the algorithm via jws-algorithms. Nimbus refetches the JWKS once on an unknown kid, so a persistent failure means the key genuinely isn't there.

    The iss claim is not validWorks locally, fails in the cluster (or the reverse)issuer
    Cause

    Issuer comparison is an exact string match. Usual suspects: trailing slash (Auth0); Entra v1 versus v2 issuer; Keycloak minting tokens with the internal URL (http://keycloak:8080/realms/acme) because the client called it in-cluster, while the API expects the public URL.

    Fix

    Copy iss from a real token into config. Pin the IdP's public hostname (Keycloak KC_HOSTNAME, proxy headers forwarded correctly). If you must accept two forms during a migration, use JwtIssuerAuthenticationManagerResolver rather than disabling the check.

    The aud claim is not validSignature and issuer pass, audience failsaudience
    Cause

    The client asked for a token for a different resource: missing audience parameter (Auth0), wrong scope (Entra: api://orders/.default versus Graph's User.Read), no audience mapper (Keycloak gives account), or Cognito access tokens with no aud at all.

    Fix

    Fix the token request, not the validator. For Cognito, validate client_id and token_use with a custom JwtClaimValidator. Removing the audience check is how a token for one API becomes a key to all of them.

    Jwt expired at 2026-10-06T08:15:00ZIntermittent 401s after some minutes, or in long batch runstime
    Cause

    The client isn't refreshing, a batch job reuses one token for an hour-long run, or a pod's clock has drifted.

    Fix

    Refresh proactively (when less than ~60 s remain) or on 401 with one retry. Let OAuth2AuthorizedClientManager handle machine tokens. Check NTP on nodes. Keep skew at 30–60 s; raising token lifetime or skew to hide the problem extends the window for stolen tokens too.

    Jwt used before 2026-10-06T08:00:00ZBrand-new tokens rejected right after logintime
    Cause

    The API's clock is behind the IdP's clock by more than the allowed skew, so nbf / iat look like the future.

    Fix

    Sync clocks (NTP, chrony). Container hosts and VMs that were suspended are the common offenders.

    403 ForbiddenToken is valid, user definitely has the roleauthorities
    Cause

    Spring's default converter only reads scope / scp and prefixes SCOPE_. hasRole("ADMIN") looks for ROLE_ADMIN. Keycloak nests roles in realm_access.roles; Entra puts app roles in roles; Cognito uses cognito:groups. None of these are mapped automatically.

    Fix

    Add a JwtAuthenticationConverter (see the Spring section). To see what you actually got, log SecurityContextHolder.getContext().getAuthentication().getAuthorities() or enable TRACE on org.springframework.security.

    PKIX path building failed / Couldn't retrieve remote JWK setAPI can't start or every request fails on a corporate networknetwork / TLS
    Cause

    The API can't fetch discovery or JWKS: a TLS-inspecting proxy with a corporate root CA the JVM doesn't trust, an outbound proxy that isn't configured, or egress blocked by a network policy or service mesh.

    Fix

    Import the corporate root CA (keytool -importcert -cacerts -alias corp-root -file corp-root.cer, or a custom truststore via -Djavax.net.ssl.trustStore); set -Dhttps.proxyHost / -Dhttps.proxyPort or give NimbusJwtDecoder.withJwkSetUri(…).restOperations(…) a configured RestTemplate; allow egress to the IdP host in the mesh. Using jwk-set-uri instead of issuer-uri removes the discovery call.

    431 Request Header Fields Too Large / 400 Request header is too largeSome users can't use the app; usually those in many groupssize
    Cause

    Groups or roles bloat the token past the server's header limit (Tomcat's default is 8 KB), or a proxy's buffer in front of it.

    Fix

    Keep tokens small: put coarse roles in the token and look up fine-grained permissions server-side. Raise server.max-http-request-header-size and proxy buffers only as a stopgap.

    Blocked by CORS policy: Response to preflight request doesn't pass access control checkWorks in Postman, fails in the browserCORS
    Cause

    The Authorization header makes the browser send an OPTIONS preflight without credentials. Spring Security answers it with 401 before CORS headers are added.

    Fix

    Enable http.cors(...) with a CorsConfigurationSource that allows your origin and the Authorization header. Spring Security then handles preflight before authentication.

    401 with an ID tokenThe frontend sends the token it got at login and the API rejects ittoken type
    Cause

    The ID token's aud is the client ID, not your API. Some frontends grab id_token because it's always a JWT.

    Fix

    Send access_token. On the API, reject ID tokens explicitly (check typ or the presence of scopes), because with a loose audience check they might otherwise pass.

    invalid_grant on refresh, then forced logoutUsers randomly logged out, often when a page fires several calls at oncerefresh
    Cause

    Several requests got 401 at once and each tried to refresh with the same refresh token. With rotation and reuse detection on, the second use revokes the whole token family.

    Fix

    Single-flight refresh: keep one shared in-flight promise (or a lock in the BFF), queue other requests behind it. Some IdPs offer a short reuse grace period; use it as a safety net, not the design.

    Token still works after logout or account disableSecurity review findingrevocation
    Cause

    That is how self-contained tokens behave: nothing checks the IdP until exp.

    Fix

    Short access-token TTL, revoke refresh tokens on logout and disable, a jti denylist (TTL = remaining lifetime) checked by a filter after JWT authentication, or introspection for high-value operations.

    All tokens invalid after the auth server restarted or scaledMass 401s right after a deploykey rotation
    Cause

    The signing key is generated in memory at startup (the Spring Authorization Server sample does this), so each restart or replica has a different key. Or a rotation started signing with a new key before consumers' JWKS caches had it.

    Fix

    Persist signing keys (keystore, KMS, vault) and share them across replicas. Rotate in the publish, wait, sign, retire order described in the algorithms section.

    Malformed token / Invalid JWT serialization: Missing dot delimiter(s)Decoder fails before any validationparsing
    Cause

    It isn't a JWT: an opaque token (Auth0 without audience, Google access token, introspection-only setups), Bearer Bearer …, quotes or a newline copied from JSON, or standard base64 instead of base64url.

    Fix

    Log the token's shape (segment count and length, never the token itself). For opaque tokens, configure opaqueToken() introspection instead of jwt().

    Service trusts X-User-Id from the gatewayAnyone inside the network can call services as any usergateway / mesh
    Cause

    The gateway validates the JWT and passes identity as plain headers; services trust those headers because "only the gateway can reach us".

    Fix

    Forward the JWT itself and validate it in every service, and strip identity headers from inbound traffic at the edge. Pair with mesh mTLS and authorization policies so only expected workloads can call each service.
