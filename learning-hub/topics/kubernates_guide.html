Container Field Manual

A container is a normal Linux process with a fence around what it can see, a budget for what it can use, and a private filesystem.

Everything else in this manual (Docker, Kubernetes, Kong Mesh, OpenShift) is machinery for building that process, placing it on machines, keeping it alive, and letting copies of it talk safely. Each chapter starts from the problem, then derives the mechanism.

Part I

The container itself

What Docker actually does to your Spring Boot jar, from the Linux kernel up.

01The problem

What a running program needs

First principle

A program only runs correctly when its whole environment matches what it was tested against. Ship the environment with the program and the mismatch disappears.

Picture what java -jar order-api.jar silently depends on. It needs a kernel to give it CPU time and memory. It needs the exact JVM version you compiled for. It needs every jar on the classpath, the operating system's C library, the CA certificates that let it make HTTPS calls, timezone data, a free port 8080, and the right values for SPRING_DATASOURCE_URL. "It works on my machine" means at least one of those differs between your laptop and the server.

There are two ways to ship the whole environment along with the program:

Ship a whole computer

A virtual machine packs its own kernel and boots like a real computer. Strong isolation, but each copy carries gigabytes and takes tens of seconds to boot.

Share the kernel, fence the process

A container reuses the host's kernel. It packs only the files above the kernel and asks the kernel to isolate the process. Start time is your JVM start time, nothing more.

Proof that a container is just a process: start one, then run ps aux | grep java on the host. Your JVM is right there in the host's process list, with a host PID. The kernel is not running a "container"; it is running a process that it has been asked to fence.

Why does a container start faster than a VM, but not faster than the app inside it?

There is no operating system to boot, because the kernel is already running. What remains is starting your process, which for Spring Boot means JVM startup plus context initialization. A container makes the environment portable; it does not make the JVM faster.

02The mechanism

The fence: namespaces, cgroups, filesystems

First principle

Isolation needs three answers: what may the process see, how much may it use, and which files make up its world. Linux has one feature for each.

See: namespaces

A namespace gives a process its own private copy of one global kernel resource. In a PID namespace your JVM believes it is process number 1. In a network namespace it gets its own interfaces, IP address and port table, so ten containers can all listen on 8080. A mount namespace gives it its own filesystem tree, and a UTS namespace its own hostname. Nothing is copied or virtualized; the kernel simply filters what the process is allowed to look up.

Use: cgroups

Seeing less is not the same as using less. A cgroup (control group) puts a budget on a group of processes: so many CPU shares per period, so many bytes of memory, so many process IDs. When memory use crosses the limit, the kernel's OOM killer ends the process. That is the origin of the famous exit code 137.

Files: a layered root filesystem

The process's / is assembled by OverlayFS: read-only image layers stacked underneath, plus one thin writable layer on top. Writing to a file from a lower layer first copies it up (copy-on-write). Delete the container and that writable layer goes with it. Anything that must survive goes in a volume.

Fence builderToggle each isolation and watch what the JVM can see

Nothing isolated yet: this is a plain java -jar on your laptop.

Two more guards complete the fence. Linux capabilities split root's powers into small pieces, and container runtimes drop most of them. seccomp filters which system calls the process may make at all. This is why "root inside a container" is weaker than root on the host, and also why it is still worth avoiding.

Your Spring Boot container writes uploaded PDFs to /tmp/uploads. After a redeploy they are gone. Why?

They lived in the container's writable OverlayFS layer, which belongs to that one container instance. A redeploy creates a new container from the image, with a fresh empty writable layer. Persist files in a volume or, better for multiple replicas, in object storage such as S3.

03Packaging

Images: a stack of filesystem diffs

First principle

If the filesystem is built from stacked diffs, then a diff that hasn't changed never needs to be rebuilt, re-uploaded or re-downloaded. Order your diffs from least to most frequently changed.

An image is two things: an ordered list of layers (each a tar archive of file changes) and a small JSON config saying which user to run as, which environment variables to set and which command to start. The whole thing is identified by a digest, a SHA-256 hash of its content. A tag like order-api:1.4.2 is just a human-friendly label that points to a digest, and it can be moved. Images live in a registry and follow the OCI format, which is why Docker, Podman, containerd and OpenShift can all share them.

A Dockerfile is a recipe where every filesystem-changing instruction produces one layer. The build cache keys each layer on its instruction plus its inputs. The moment one layer misses the cache, every layer above it is rebuilt too, because each diff is defined relative to the one below.

Why the fat jar fights the cache

A Spring Boot fat jar bundles 60 MB of dependencies with 300 KB of your code in one file. Copy it into the image and it becomes one layer, so changing one line in a controller re-ships all 60 MB. Spring Boot's layered jar fixes this by splitting the jar into four directories ordered by how often they change. Try both below.

Layered: a code change only rebuilds the top layer.

A production Dockerfile uses a multi-stage build: a heavy JDK + Maven stage compiles, and only the extracted layers are copied into a slim JRE stage. The build tools never reach production.

Dockerfile · multi-stage, layered, OpenShift-friendly
# ---- stage 1: build (JDK + Maven, thrown away afterwards) ----
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw -q dependency:go-offline          # cached until pom.xml changes
COPY src src
RUN ./mvnw -q package -DskipTests
# split the fat jar into its layers (Boot 3.3+ "tools" jarmode)
RUN java -Djarmode=tools -jar target/order-api.jar extract --layers --launcher --destination /x

# ---- stage 2: runtime (JRE only) ----
FROM eclipse-temurin:21-jre
WORKDIR /app
# least to most frequently changed = best cache reuse
COPY --from=build /x/dependencies/ ./
COPY --from=build /x/spring-boot-loader/ ./
COPY --from=build /x/snapshot-dependencies/ ./
COPY --from=build /x/application/ ./
# group 0 + group-writable: survives OpenShift's random UID (chapter 18)
RUN chgrp -R 0 /app && chmod -R g=u /app
USER 1001
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75"
EXPOSE 8080
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

Two ways to skip the Dockerfile

  • Buildpacks: mvn spring-boot:build-image. Detects a Java app, picks a JRE, applies the layering, sets memory flags from the container limit, and runs as a non-root user. Needs a Docker daemon.
  • Jib: a Maven/Gradle plugin that builds layered images straight from your class files and pushes to a registry without any Docker daemon. Ideal in CI.

Housekeeping that pays off: a .dockerignore (keep target/ and .git out of the build context), pinning base images by digest for reproducible builds, and preferring JRE-only or distroless bases, since every package you leave out is one less thing to patch.

Why put COPY pom.xml and dependency:go-offline before COPY src?

Layers are cached by their inputs. pom.xml changes rarely, so the slow dependency download layer stays cached across almost every build. If src were copied first, every code edit would invalidate the dependency layer and Maven would download the internet again.

04Runtime behaviour

PID 1, signals and graceful shutdown

First principle

A platform stops your container by sending a polite signal, waiting, then forcing it. Your app only gets the polite signal if it is the process receiving it.

Inside its PID namespace, the first process is PID 1. When Docker or Kubernetes wants it gone, it sends SIGTERM to PID 1, waits a grace period (10 s in Docker, 30 s by default in Kubernetes), then sends SIGKILL, which cannot be caught.

The trap is the ENTRYPOINT form. Write ENTRYPOINT java -jar app.jar (shell form) and PID 1 becomes /bin/sh, which does not forward SIGTERM to Java. Your app never hears the request to stop, gets killed mid-request, and the client sees a dropped connection. Write the JSON exec form, ["java","-jar","app.jar"], and Java is PID 1.

Once Java receives SIGTERM, Spring Boot can drain cleanly:

application.yml
server:
  shutdown: graceful                 # stop accepting, finish in-flight requests
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s  # must be shorter than the platform's grace period
Exit codeWhat happenedUsually means
0Process ended normallyA Job finished, or the app shut down cleanly
1Uncaught exception at startupBad config, missing bean, DB unreachable. Read the logs.

Logs and config: let the platform own them

Write logs to stdout, not to files. The runtime already captures stdout, and a log file inside the container dies with its writable layer. Read configuration from environment variables: Spring's relaxed binding turns SPRING_DATASOURCE_URL into spring.datasource.url, so the same image runs in every environment. This is the twelve-factor idea: build once, configure at deploy time.

Pods return 502s for a few seconds during every deploy. What two things do you check first?

First, that the ENTRYPOINT uses exec form so Java actually receives SIGTERM. Second, that server.shutdown=graceful is set and finishes inside the grace period. Chapter 12 adds the third piece: a short preStop delay so the load balancer stops sending traffic before the app stops accepting it.

05Java specifics

The JVM inside a fence

First principle

The JVM sizes itself from the resources it believes it has. Inside a cgroup, the only honest number is the cgroup's limit, and the heap is only one part of what the JVM spends.

Old JVMs read /proc/meminfo and saw the whole host. A JVM in a 512 MiB container on a 16 GiB node would plan a 4 GiB heap and get killed by the kernel. Since JDK 10 (and 8u191), the JVM is container-aware and reads the cgroup limit instead. But its default maximum heap is only 25% of that limit, which wastes most of the container. That is why -XX:MaxRAMPercentage exists.

Do not set it to 100%. The process also spends memory on metaspace (class metadata), one stack per thread (about 1 MiB each, and Tomcat defaults to 200 worker threads), the JIT code cache, direct byte buffers used by Netty and NIO, and the garbage collector's own bookkeeping. The kernel counts all of it.

OOMKilled

Notice the two different failures. java.lang.OutOfMemoryError means the heap is full, so the JVM complains and you get a stack trace. OOMKilled means the whole process exceeded the cgroup and the kernel ended it without a word: no stack trace, exit code 137. The first is a code or heap-size problem; the second is usually a budget problem outside the heap.

CPU is a budget too

A CPU limit of 1 means 100 ms of CPU time per 100 ms window. Spend it early in a garbage collection and the kernel pauses your process for the rest of the window: CPU throttling. You see it as random latency spikes, not as high CPU. The JVM also derives its GC thread count and the ForkJoinPool size from the CPU limit, so a tiny limit makes a slow JVM. Many teams set CPU requests but no CPU limit for Java services for this reason.

Startup time matters when the platform scales and restarts you. Class Data Sharing, Spring AOT processing and lazy initialization each shave seconds; virtual threads reduce how many platform-thread stacks you pay for.

A pod is OOMKilled but heap dumps show the heap only 60% full. Where is the memory?

Outside the heap: thread stacks (count your threads with jcmd <pid> Thread.print), metaspace from many classes, direct buffers from Netty/Kafka clients, or native allocations. Enable -XX:NativeMemoryTracking=summary and run jcmd <pid> VM.native_memory summary to get the breakdown, then lower MaxRAMPercentage or raise the limit.

06One host, many containers

Networking, volumes and Compose

First principle

Every container has its own network namespace, so localhost means "this container", never "the machine". Containers find each other by name through a shared network, not by address.

Docker connects containers through a virtual bridge network. On a user-defined network Docker also runs a small DNS server, so the container named postgres is reachable at the hostname postgres. The classic beginner bug is an app container configured with jdbc:postgresql://localhost:5432: inside the app container, nothing is listening on 5432.

To reach a container from your laptop you publish a port: -p 8080:8080 maps host port to container port. For data, choose between a named volume (Docker manages the storage; good for databases), a bind mount (a host folder, good for local config) and tmpfs (memory only).

compose.yaml · app + database, started in order
services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_DB: orders
      POSTGRES_USER: orders
      POSTGRES_PASSWORD: changeme
    volumes: [pgdata:/var/lib/postgresql/data]   # survives container removal
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U orders"]
      interval: 5s
      retries: 10

  order-api:
    image: order-api:0.0.1
    ports: ["8080:8080"]                         # host:container
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/orders   # service name, not localhost
      SPRING_DATASOURCE_PASSWORD: changeme
    depends_on:
      postgres: { condition: service_healthy }    # wait for a real health check
    mem_limit: 512m

volumes:
  pgdata: {}

Compose is the right tool for one machine: your laptop or a CI job. For integration tests, Testcontainers starts the same Postgres or Kafka images from inside JUnit. Once you need many machines, automatic restarts and rolling deploys, you need the next part.

Compose starts order-api after postgres, yet the app still fails with "connection refused" without the healthcheck. Why?

Plain depends_on waits only until the postgres container has started, not until Postgres is accepting connections, which takes a few seconds longer. The healthcheck plus condition: service_healthy waits for real readiness. Kubernetes solves the same problem differently, with readiness probes and retries.

Part II

Kubernetes

From one machine to a fleet: the same container, now placed, healed, discovered and scaled for you.

07The core idea

Desired state and the reconcile loop

First principle

Instead of giving the system instructions ("start 3 containers"), you write down the outcome ("3 should exist") and let small programs keep reality equal to it forever.

With many machines, new questions appear. Which machine has room for this container? Who restarts it when the machine dies? How do other services find it once its IP changes? How do I roll out version 2 without downtime? A script that runs commands once answers none of these, because the world keeps changing after the script ends.

Kubernetes is declarative. You store desired state as an object in the API. A controller runs a reconcile loop: observe the actual state, diff it against the desired state, act to close the gap, repeat. Because it keeps comparing levels instead of reacting to individual events, a missed event does no lasting harm; the next loop catches the difference.

Reconcile loopChange the desired count or kill a pod, then watch the controller react
spec.replicas 3
observediffact

Pause the controller and kill pods: nothing heals. That is the whole point. Kubernetes is not magic; it is dozens of these loops running all the time.

You run kubectl delete pod order-api-7d9f… and a new pod appears seconds later. You wanted it gone. What do you change instead?

The pod is owned by a ReplicaSet whose desired count didn't change, so the controller replaced it. Change the desired state instead: kubectl scale deployment order-api --replicas=2, or edit the replicas in your manifest or Helm values.

08Who does what

Cluster architecture

First principle

One component stores the truth, everything else watches it. Every part of Kubernetes talks only to the API server; no component calls another directly.

Follow one kubectl apply -f deployment.yaml through the machine. These steps really are a sequence:

  1. kubectl sends the YAML to the API server, which authenticates you, checks RBAC, runs admission checks and stores the Deployment in etcd.
  2. The Deployment controller (inside the controller-manager) sees a Deployment with no ReplicaSet and creates one. The ReplicaSet controller sees zero pods out of three and creates three Pod objects. Nothing runs yet; these are just records.
  3. The scheduler sees pods with no node, scores the nodes by free requests, affinity and spread, and writes a node name into each pod.
  4. The kubelet on that node sees a pod assigned to it and asks the container runtime (containerd or CRI-O, through the CRI) to pull the image and start the containers. The CNI plugin gives the pod an IP.
  5. The kubelet runs probes and reports status back to the API. When the pod is ready, endpoint controllers add its IP to matching Services and kube-proxy updates routing rules on every node.

Every arrow points at the API server. That design is why a cluster can survive any one component restarting: each one simply re-reads the state and continues its loop.

09Deriving the objects

Workloads: Pod to Deployment and beyond

First principle

Every workload object exists because the one below it lacks exactly one guarantee. Learn the missing guarantee and you know the object.

ObjectProblem it solvesWhat it still lacks
PodGroups containers that must share a network namespace and volumes (app + sidecar, plus init containers that run first)Mortal. If its node dies, nothing recreates it. Its IP changes every time.
ReplicaSetKeeps N identical pods aliveNo idea of versions. Changing the image does not replace running pods.
DeploymentOwns ReplicaSets per version and moves pods from old to new in a controlled rolling update, with rollbackPods are interchangeable: random names, shared or no storage

The glue between all of them is the label. A ReplicaSet does not keep a list of its pods; it runs a selector query (app=order-api) on every loop. A Service finds its pods the same way. Get a label wrong and objects silently stop finding each other.

10Same image, every environment

ConfigMaps, Secrets and Spring

First principle

An image that contains environment-specific settings has to be rebuilt per environment, so what you tested is not what you ship. Keep configuration outside the image and inject it at start.

A ConfigMap holds plain settings; a Secret holds sensitive ones. Both reach the pod as environment variables or as files in a mounted volume. One distinction matters: environment variables are fixed when the container starts, while mounted files are updated in place (after a short delay) when the object changes.

Know what a Secret is not. Its values are base64-encoded, not encrypted. Anyone allowed to read Secrets in the namespace can decode them. Real protection comes from RBAC, encryption at rest in etcd, and often an external store such as Vault or a cloud secrets manager synced in by an operator.

Spring reads mounted Secrets as properties with configtree
# pod spec: mount each Secret key as a file
volumes:
  - name: db
    secret: { secretName: order-api-db }        # keys: spring.datasource.username, spring.datasource.password
containers:
  - name: app
    volumeMounts: [{ name: db, mountPath: /etc/secrets/db, readOnly: true }]

# application.yml: each file name becomes a property name, content its value
spring:
  config:
    import: "optional:configtree:/etc/secrets/*/"

The configtree import keeps secrets out of environment variables, where they can leak through /actuator/env, crash dumps or child processes. Profiles still work: set SPRING_PROFILES_ACTIVE=prod from a ConfigMap.

You updated a ConfigMap, but the running app still uses the old value. Why, and what are the two fixes?

If the value arrives as an environment variable, it was copied into the process at start and never changes. Either restart the pods (kubectl rollout restart deployment/order-api, or have Helm add a checksum annotation so config changes trigger a rollout), or mount it as files and have the app re-read them.

11Finding each other

Services, DNS, Ingress

First principle

Pods are cattle: they come and go with new IPs. Clients need one name that never changes and always points at whichever pods are currently healthy.

Every pod gets its own IP from the CNI plugin, and every pod can reach every other pod directly. But those IPs change with each restart. A Service provides a stable virtual IP and DNS name. Behind it, an EndpointSlice lists the IPs of pods that match the Service's selector and are ready. kube-proxy turns that list into iptables, IPVS or eBPF rules on every node, so a connection to the virtual IP lands on one real pod.

From any pod, CoreDNS resolves payment-api (same namespace) or payment-api.payments.svc.cluster.local (anywhere). Your Spring RestClient just calls http://payment-api:8080.

"DB down" fails only readiness: the pod stays alive but leaves the endpoint list. "Hang JVM" fails liveness too: after 3 failures the kubelet restarts the container.

North-south traffic: Ingress and Gateway API

Services are layer 4: IPs and ports. Traffic from outside the cluster (north-south) usually needs layer 7: hostnames, paths, TLS certificates. An Ingress object describes those rules, and an ingress controller (NGINX, Traefik, Kong Gateway, HAProxy) implements them. The newer Gateway API splits the same job into roles: platform teams own the Gateway, app teams attach HTTPRoutes.

By default every pod can call every other pod. A NetworkPolicy turns that into an allowlist, and in regulated environments the norm is deny-all plus explicit allows.

A Service exists, the pods are Running, but calls time out. kubectl get endpointslices shows no addresses. Name two causes.

Either the Service selector does not match the pod labels (compare kubectl get pods --show-labels with the Service spec), or the pods are not ready because their readiness probe fails. Both leave the endpoint list empty, so there is nowhere to route.

12Alive is not ready

Probes with Spring Boot Actuator

First principle

The platform needs two different answers: "should I kill and restart you?" and "should I send you traffic right now?" Mixing them up turns a small outage into a big one.

ProbeQuestionOn failureSpring Boot endpoint
StartupHave you finished booting?Keeps the other probes paused; restarts after the threshold/actuator/health/liveness
LivenessAre you stuck beyond self-repair?Container restart/actuator/health/liveness
ReadinessCan you serve a request right now?Removed from Service endpoints; not restarted/actuator/health/readiness

Spring Boot Actuator exposes both groups automatically when it detects Kubernetes, backed by LivenessState and ReadinessState in the application context. During startup, readiness stays REFUSING_TRAFFIC until all ApplicationRunners finish; during shutdown it flips back, so traffic drains before the app stops.

The most expensive mistake: never put external dependencies in liveness. If the database goes down and liveness checks the database, every pod fails liveness at once and the kubelet restarts the whole fleet in a loop, which does nothing for the database and adds cold-start load when it returns. Dependencies belong in readiness, if anywhere.

application.yml · probe groups
management:
  endpoint:
    health:
      probes:
        enabled: true                  # on automatically in K8s; explicit for local tests
      group:
        liveness:
          include: livenessState       # only "is the JVM healthy", never the DB
        readiness:
          include: readinessState, db  # optional: stop traffic while DB is unreachable
  endpoints:
    web:
      exposure:
        include: health, info, prometheus

The shutdown sequence ties chapters 4, 11 and 12 together. On delete, Kubernetes removes the pod from endpoints and sends SIGTERM at roughly the same moment, but the endpoint removal takes a second or two to reach every node. A short preStop sleep keeps the app accepting requests until no one routes to it any more; then graceful shutdown finishes what is in flight.

13Placement and size

Requests, limits, QoS and autoscaling

First principle

A scheduler can only pack machines safely if every pod states what it needs. A node can only stay healthy if every pod has a ceiling.

A request is a reservation: the scheduler places the pod only on a node with that much unreserved capacity, and the pod is guaranteed it. A limit is a ceiling enforced by the cgroup: memory over the limit means OOMKilled, CPU over the limit means throttling. CPU is measured in millicores (250m is a quarter of a core), memory in bytes (512Mi).

The combination sets the pod's QoS class, which decides who gets evicted first when a node runs out of memory:

QoS classRuleEviction order
Guaranteedrequests = limits for CPU and memory in every containerLast
BurstableSome request set, not equal to limitsMiddle
BestEffortNo requests or limits at allFirst

For a Spring Boot service a sound default is: memory request equal to memory limit (the JVM heap does not shrink back, so bursting memory only invites OOM kills), and a CPU request with no CPU limit (so startup and GC can burst instead of being throttled).

Horizontal Pod Autoscaler

The HPA is another reconcile loop. Every 15 seconds it computes desired = ceil(current × currentMetric ÷ target). Three pods at 90% CPU against a 60% target gives ceil(3 × 90 ÷ 60) = 5. CPU percent is measured against the request, so a missing request makes the HPA blind. For queue consumers, scale on lag instead (KEDA does this for Kafka and SQS).

A PodDisruptionBudget protects you from voluntary disruptions such as node drains during cluster upgrades: minAvailable: 2 stops a drain from evicting below two ready pods. To spread replicas across nodes and zones, use topology spread constraints or pod anti-affinity; taints and tolerations keep pods off nodes reserved for something else.

A pod sits in Pending forever while the cluster's dashboard shows nodes at 30% CPU usage. How can that be?

The scheduler counts requests, not live usage. If existing pods have requested most of each node's CPU, there is no unreserved room left even though actual usage is low. kubectl describe pod shows a FailedScheduling event with "Insufficient cpu". Right-size the requests or add nodes.

14Data that outlives pods

Persistent volumes

First principle

Separate "I need 10 GiB of disk" (what the app asks for) from "here is an EBS volume in zone b" (what the infrastructure provides), so app manifests stay portable across clusters.

A PersistentVolumeClaim is the app's request: size and access mode. A PersistentVolume is a real piece of storage. A StorageClass lets the cluster create a PV on demand when a claim appears (dynamic provisioning). Access modes matter: ReadWriteOnce attaches to one node at a time (block disks), ReadWriteMany lets many pods on many nodes share it (network filesystems).

A StatefulSet's volumeClaimTemplates gives each replica its own claim (data-postgres-0, data-postgres-1), reattached to the same identity after rescheduling. In practice, most teams run production databases as managed services and keep Kubernetes storage for brokers, caches and labs. Stateless Spring services should not need a volume at all; use object storage for files.

15Getting manifests to clusters

Helm, Kustomize and GitOps

First principle

Dev, test and prod manifests are 95% identical. Write the shared part once and express only the differences, then let a reconcile loop apply them from Git.

Helm

Templates plus a values.yaml per environment. Installs are tracked as numbered releases, so helm rollback order-api 3 restores an earlier set of manifests. Good for packaging and sharing apps.

Kustomize

No templating: a plain YAML base plus overlays that patch it per environment. Built into kubectl apply -k. Good when you want the YAML to stay plain YAML.

GitOps

Argo CD or Flux watches a Git repo and keeps the cluster equal to it. It is the reconcile loop from chapter 7, one level up: Git holds desired state; manual kubectl edit drift gets reverted.

Part III

Service mesh and Kong Mesh

Moving retries, timeouts, encryption and identity out of every service and into the platform.

16The problem

Why a service mesh exists

First principle

When fifty services each reimplement mTLS, retries, timeouts and metrics in their own library and language, they do it fifty slightly different ways. Put one proxy next to every service and configure all of them from one place.

Every network call between services (east-west traffic) needs the same things: encryption and proof of identity (mTLS), timeouts, retries with backoff, circuit breaking, load balancing, metrics and trace propagation. In Spring you can do much of this with Resilience4j and Micrometer, but only in Java, only if every team configures it the same way, and only by redeploying apps to change a timeout.

A service mesh splits the job in two. The data plane is a proxy, almost always Envoy, injected as a sidecar into every pod. A transparent proxy setup rewrites the pod's iptables rules so all traffic in and out goes through it, without the app changing a line. The control plane turns your policies into Envoy configuration, issues each proxy a certificate that encodes its identity, and pushes both to every proxy.

The cost is real: an extra hop (typically well under a millisecond each way), memory per sidecar, and one more system to debug. Newer "sidecarless" designs (Istio ambient, Cilium) move the proxy to the node to reduce that cost; the concepts stay the same.

17The product

Kong Mesh in practice

First principle

A mesh is only as good as its policy model. In Kong Mesh every policy answers two questions: which proxies does it configure, and for traffic to or from whom.

Kong Mesh is Kong's enterprise distribution of Kuma, an open-source CNCF mesh built on Envoy. The control plane is kuma-cp; the sidecar is kuma-dp, a small agent that runs and configures Envoy. Each proxy is registered as a Dataplane object. Kong Mesh adds enterprise features on top of Kuma: certificate authorities backed by HashiCorp Vault or cloud PCA, OPA policy, FIPS-compliant builds, role-based access to mesh resources and support.

Two properties make it attractive for banks and large enterprises. It runs on Kubernetes and on plain VMs ("Universal mode"), so legacy services can join the same mesh. And it supports multi-zone deployments: a global control plane holds policies, zone control planes in each cluster or data centre apply them, and zone ingress and egress proxies carry cross-zone traffic.

Do not confuse it with Kong Gateway. The gateway is the API front door for north-south traffic: authentication plugins, rate limits for partners, developer portal. The mesh handles east-west traffic between your own services. They work together; a gateway can run inside the mesh so it too speaks mTLS to backends.

The policy model

Modern Kuma/Kong Mesh policies share one shape. A targetRef at the top selects which proxies receive the configuration (the whole Mesh, a set of Dataplanes by label, or one MeshService). A to section configures outbound traffic toward destinations; a from section configures inbound traffic from sources.

What changes in your Spring Boot app

  • Call by Service name over plain HTTP. http://payment-api.payments:8080. The sidecar handles TLS; adding your own TLS on top is double work.
  • Remove duplicate retries. If the app retries 3 times, the mesh retries 3 times, and the next hop does the same, one user click becomes 3 × 3 × 3 = 27 calls against a struggling service: a retry storm. Retry in exactly one layer.
  • Make timeouts nest. The caller's total timeout must be longer than the mesh's per-try timeout times the number of attempts, or the app gives up while the mesh is still retrying.
  • Propagate trace headers. The proxy creates spans, but only your app can copy the incoming traceparent header onto outgoing calls. Micrometer Tracing does this for RestClient, WebClient and Kafka templates.
  • Probes and shutdown. With strict mTLS the kubelet cannot reach your app directly, so the mesh rewrites HTTP probes to go through the sidecar. On shutdown the sidecar must outlive the app or in-flight outbound calls fail; native Kubernetes sidecar containers (1.29+) solve this ordering.

Debugging the mesh

Most mesh failures surface as a 503 with an Envoy response flag in the access log: UF (could not connect upstream), UH (no healthy upstream), UT (upstream timeout), URX (retry limit reached), NR (no route). A denied permission typically shows as 403 RBAC: access denied or a reset connection. Start with kumactl inspect dataplanes and the mesh GUI, then look at the proxy's own view of its config through Envoy's admin config_dump.

After enabling mTLS mode strict, a service that is not yet in the mesh can no longer call payment-api. Why?

In strict mode the receiving sidecar accepts only mTLS connections with a valid mesh certificate. A service without a sidecar has no certificate, so it cannot prove an identity. Kuma's permissive mode accepts both plaintext and mTLS during a migration; switch to strict once every caller has a sidecar.

Part IV

OpenShift

Kubernetes with Red Hat's opinions built in: security on by default, builds in the cluster, and a developer console.

18The distribution

What OpenShift adds to Kubernetes

First principle

Plain Kubernetes leaves many choices open: ingress, builds, registry, security defaults. OpenShift makes those choices for you, and the strictest one is that your container may not decide who it runs as.

Everything from Part II still applies: Deployments, Services, ConfigMaps and probes work unchanged, and the oc CLI accepts every kubectl command. OKD is the community upstream. What you meet on top:

Security Context Constraints and the random UID

The default SCC (restricted-v2) runs your container as an arbitrary UID, a high random number from the project's assigned range, with group 0. Your Dockerfile's USER 1001 is overridden. An image that expects to own /app as user 1001, or that runs as root, fails with "permission denied" or does not start at all.

The fix comes from first principles: the UID is unpredictable, but the group is always 0. So give group 0 the same rights as the owner on every directory the app writes to. That is the chgrp -R 0 /app && chmod -R g=u /app line in the chapter 3 Dockerfile. Buildpack images already follow this rule.

Routes

A Route predates Ingress and does the same job with built-in TLS modes, served by the HAProxy-based router: edge (TLS ends at the router), passthrough (TLS goes straight to your pod) and reencrypt (the router decrypts, then opens a new TLS connection to the pod). OpenShift also accepts Ingress objects and converts them into Routes.

route.yaml · or simply: oc create route edge order-api --service=order-api
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: order-api
spec:
  host: orders.apps.example.com
  to: { kind: Service, name: order-api }
  port: { targetPort: http }
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect   # http → https

Builds inside the cluster

A BuildConfig builds images in the cluster itself. Source-to-Image takes a Git URL and a builder image (for example ubi9/openjdk-21), runs Maven, and produces a runnable image with no Dockerfile. A binary build uploads a jar you built locally. Results land in an ImageStream, OpenShift's pointer to images in the internal registry, which can trigger a redeploy when a tag moves.

Terminal · S2I from Git, then a binary build from your local jar
oc new-project orders-dev                                   # a Project = namespace + defaults

  --name=order-api

# binary build: skip Git, upload target/ from your laptop

Other OpenShift pieces you will meet

  • Projects: namespaces with extra metadata, default quotas and the UID range used by the SCC.
  • DeploymentConfig: OpenShift's older deployment object, deprecated since 4.14. Use a standard Deployment; you will still read DCs in older projects.
  • Templates: parameterized object lists, OpenShift's answer before Helm. Helm charts now work everywhere, including OpenShift.
  • Operators and OLM: a CRD plus a controller that runs a piece of software for you (Kafka via Strimzi/AMQ Streams, Postgres, Kong Mesh itself). OperatorHub in the console installs them.
  • Web console: a Developer perspective with a Topology view of your apps, builds, routes and logs. Kubernetes has no built-in equivalent.

20When it breaks

Observability and the triage playbook

First principle

In a fleet of disposable pods you cannot SSH in and look around later. Every answer you might need must be emitted while it happens: logs, metrics and traces, all tagged with the same IDs.

Logs go to stdout as structured JSON with the trace ID in every line (Spring Boot 3.4+ has built-in structured logging: logging.structured.format.console=ecs). Metrics come from Micrometer at /actuator/prometheus: request rate, errors and latency per endpoint, plus JVM memory, GC pauses and connection pool usage. Traces follow one request across services through the traceparent header; with a mesh, the proxies add spans for every hop.

Most incidents start with one of six pod states. kubectl describe pod shows the Events section, which answers most of them before you read a single log line.
