Start with one idea

Every vulnerability in this guide is the same mistake in a different costume. A program accepted data from someone it should not fully trust, then handed that data to something that gives it power.

Power takes different forms. An {{interpreter}} such as a database runs the text as a command. A browser runs it as script. A file system follows it to another directory. An {{authorization}} check never happens, so a number in the URL becomes proof that you may read a record. Learn to spot the handoff and you can review any code base in any language.

Five questions that drive every review

  1. What are we protecting? These are the {{asset}}s: money, personal data, credentials, availability.
  2. Who might attack, and with what starting access? That is the {{threat-actor}}: an anonymous visitor, a customer, an insider.
  3. Where does untrusted data enter? That is the {{attack-surface}}: every endpoint, header, file, queue message and dependency.
  4. Where does that data gain power? Those are the {{sink}}s: queries, shells, file calls, renderers, deserializers.
  5. What stands in between? Validation, encoding, parameter binding, authorization checks. Where nothing does, you have a finding.

Where a Java application has boundaries

A trust boundary is a line where the level of trust changes. Data crossing it needs a decision: validate it, encode it, authorize it, or refuse it. Select a stage below, or follow one request from the outside in.

Four habits that guide every decision

{{least-privilege}}
Give each component, account and token only what its job needs. A stolen credential then opens one door instead of the building.
{{defense-in-depth}}
Assume any single control fails. Validation, parameterized queries, a restricted database account and monitoring each catch what the others miss.
{{fail-closed}}
When a check cannot decide, deny. An exception inside an authorization filter should end in a 403, not in access.
Verify, do not assume
Frameworks help and do not guarantee. Thymeleaf escapes output in th:text and not in th:utext. Spring Data binds parameters in derived queries and not in a JPQL string you concatenated yourself.

How risky is it?

Risk is likelihood times impact. Impact is judged on the {{cia-triad}}: {{confidentiality|confidentiality}} (who can read it), {{integrity}} (who can change it) and {{availability}} (whether it stays up). The penetration testing part turns this into a number with {{cvss}}, and the reporting part turns that number into a deadline.

A review is a funnel

A scoped map narrows what to look at. Tools read the repetitive parts. A person reads what needs context. Tests prove only what must be proven. The report makes the fix obvious.

Map the attack surface and the critical paths

Write down what you are reviewing and what you may touch. Then list the {{attack-surface}}: controllers and routes, message listeners, scheduled jobs, file uploads, admin consoles and third-party callbacks. Mark the critical paths: login, password reset, and anything that moves money or changes permissions. Note the data stores and where secrets live.

Authorization comes first. Confirm written authorization and the {{roe}} before any active step. Reading code you were handed is one thing. Sending traffic to a running system is another, and it needs written permission.

Let machines cover the breadth

Run {{sast}}, dependency and secret scanners before reading by hand. They are fast, consistent and tireless on the repetitive part of the work.

Pick tools that fit the language. The Java choices are in the Scanning part.

Read what tools cannot understand

Tools match patterns. They cannot know that customer A must not read customer B's invoice. A person who understands the business rules has to read the code. Skipping this step is the most expensive shortcut in the whole workflow.

  • {{authentication}} first: how is identity proven, and how long does it last?
  • {{authorization}} on every endpoint and every object, not only on the menu that links to it.
  • Input handling: which values reach a {{sink}} and what stands in between?
  • Cryptography: password hashing, key storage, TLS settings, random number sources.

Prove it once, then stop

Verify written scope authorization before active testing. Validate each finding, rate it with {{cvss}} as Critical, High, Medium, Low or Info, and confirm exploitability with a {{poc}} only. A proof of concept shows the flaw is real. It never extracts real data or damages anything.

Make the fix obvious

Confirm findings with the stakeholder before finalizing. For each one record the location, the impact and the remediation. Report critical findings immediately instead of waiting for the final document.

Always

  • Check authentication and authorization first
  • Run automated tools before manual review
  • Give specific file and line locations
  • Include remediation for each finding
  • Rate severity consistently
  • Check for secrets in code
  • Verify scope and authorization before active testing
  • Document all testing activity
  • Follow the rules of engagement
  • Report critical findings immediately

Never

  • Skip manual review, because tools miss things
  • Test production systems without authorization
  • Ignore low severity issues
  • Assume the framework handles everything
  • Share detailed exploits publicly
  • Exploit beyond a proof of concept
  • Cause service disruption or data loss
  • Test outside the defined scope

Opening a Spring Boot repository

A good first hour follows this order, because each file tells you what to trust in the next.

  1. The security configuration (a SecurityFilterChain bean). Which paths are open? Is {{csrf}} protection on for browser sessions? Is the session or token setup sound?
  2. Controllers and their request objects. What gets bound from the request, and is it validated?
  3. Repositories and any native queries. How is each statement assembled?
  4. The application.yml files and profiles: credentials, actuator exposure, debug flags, CORS.
  5. The build file (pom.xml or build.gradle) for outdated or vulnerable dependencies.
  6. The Dockerfile, Kubernetes manifests and CI configuration.

Let tools read the repetitive parts

A scanner is a fast reader with a short memory. It knows thousands of patterns and nothing about your business rules.

How static analysis thinks

{{sast}} follows data through code looking for a path from a {{source}} to a {{sink}} that skips every {{sanitizer}}. That technique is called {{taint}} analysis. Two neighbours cover what it cannot: {{sca}} checks your libraries against known vulnerabilities, and {{dast}} attacks the running application from outside.

Put it in the pipeline

A scan that runs on every push finds problems while the author still remembers the code. Gate the build on severity so that noise does not train people to ignore the tool.

What the tools will miss

Missing checks

A controller that never asks who the caller is looks like valid code. No pattern matches an absent line. This is why {{idor|IDOR}} is mostly found by people.

Business rules

A negative quantity that refunds money, a discount applied twice, a race between two requests. These are logic, and logic is specific to your product.

Design and configuration

An internal service that trusts any caller on the network, or a setting that lives in another repository. The scanner never sees them.

Expect {{false-positive}}s and some {{false-negative}}s. Triage every result, keep a short suppression list with reasons, and never treat a clean report as proof of safety.

Seven patterns, one shape

For each pattern, find the handoff, name what the receiver does with the data, and check what stands in between. Switch each tab between the vulnerable and the secure Java code and watch which line changes.

First principle. The SQL engine cannot tell your text from the user's text unless they travel in separate channels. A {{parameterized-query}} sends the statement and the values separately.

Find it
String concatenation or String.format feeding Statement, createNativeQuery or a JPQL string. A derived Spring Data method such as findByName binds parameters. A @Query built with + does not.
Prove it safely
On a test system, send a harmless marker or cause a short time delay and observe the response. Never read or change real rows.
Maps to
CWE-89, OWASP A03 Injection
An {{orm}} does not rescue you. Hibernate and JPA bind parameters only when you let them. Concatenate user input into a JPQL string and you have the same bug one layer up.

First principle. The browser cannot tell your markup from the user's text unless you encode the text for the place it lands. One value needs different encoding in an HTML body, an attribute, a script block and a URL.

Find it
Servlet or JSP code that writes request values straight into the response, th:utext, and in browser code innerHTML, document.write and React's dangerouslySetInnerHTML. React and Thymeleaf escape by default, so the unsafe forms are the ones to hunt.
Prove it safely
Submit a unique marker string and check whether it comes back unencoded in the HTML. Reach for a script-execution proof only if reflection is ambiguous, and use a harmless action such as showing the page's domain.
Maps to
CWE-79, OWASP A03 Injection. A {{csp}} header limits the damage when encoding is missed somewhere.

First principle. The file system resolves .. segments after your code has joined the strings. Compare the resolved path with the directory you meant to allow. That comparison is {{canonicalization}}.

Find it
Any new File(...), Paths.get(...) or resolve(...) whose argument traces back to a request value, including archive entry names when you unzip uploads.
Prove it safely
Ask for a harmless file that exists on every test system outside the upload directory, and stop once you see it is served. Do not browse the file system.
Maps to
CWE-22, OWASP A01 Broken Access Control

First principle. A shell reads one string and decides where commands begin and end. Pass an argument list instead and no shell gets to decide. Even then, a value that starts with a dash can be read as an option, which is {{argument-injection}}.

Find it
Every ProcessBuilder and Runtime.exec call, and especially any that start sh -c or cmd /c. Then ask whether a library could do the job without a process at all.
Prove it safely
Show command output that proves control without touching data, such as the output of id or whoami, on a test system you are authorized to use.
Maps to
CWE-78, OWASP A03 Injection

First principle. An identifier is a name, not a permission. Authentication says who is asking. Only an explicit check says whether this caller may touch this record.

Find it
For every endpoint that takes an ID in the path, query or body, ask where the code compares the record's owner with the caller. If nothing does, it is a finding, and no scanner will point at the missing line.
Prove it safely
Use two test accounts. Log in as B, request A's record, and expect a denial. Evidence is the two accounts, the IDs and the responses.
Maps to
CWE-639, OWASP A01 Broken Access Control. Returning 404 instead of 403 also avoids confirming that the record exists.

First principle. Deserializing means building objects from bytes, and building objects runs code. If the sender chooses which classes get built, the sender chooses which code runs. A {{gadget-chain}} stitches together classes that already exist on your classpath.

Find it
ObjectInputStream.readObject on anything from outside, Jackson default typing, and YAML loaders that construct arbitrary types. Check which libraries sit on the classpath.
Prove it safely
Usually confirm by code review and by checking for the vulnerable library version. Avoid running payloads against shared systems.
Maps to
CWE-502, OWASP A08 Software and Data Integrity Failures. Use an {{objectinputfilter}} when native serialization cannot be removed.

First principle. Everything your application writes outward, in logs, error pages and API responses, crosses a boundary too. Treat output as data leaving, and decide what is allowed to leave.

Find it
Log statements that include credentials or tokens, printStackTrace, responses that return whole entities, and Spring settings that include stack traces in error bodies. Set server.error.include-stacktrace to never.
Prove it safely
Trigger a normal error on a test system and read the response and the log line. Redact anything real before it goes into the report.
Maps to
CWE-200, CWE-209, CWE-532, OWASP A09 Logging Failures

The OWASP Top 10 through a Java lens

The {{owasp-top-10}} groups these patterns into ten categories. The mapping below follows the 2021 list used in the reference material. Check owasp.org for the current edition before you cite it in a report.

A01 Broken Access Control IDOR, path traversal
Default to deny: end the filter chain with anyRequest().authenticated(). Check ownership in the query, not in the user interface. Test with two accounts.
A02 Cryptographic Failures weak encryption, plaintext
Hash passwords with BCrypt or Argon2 (BCryptPasswordEncoder), never MD5 or SHA-1. Use TLS everywhere, AES-GCM instead of ECB, and keep keys out of the repository.
A03 Injection SQL, XSS, command
Parameterize every query, encode every output, never build shell strings. The three tabs above cover the Java forms.
A04 Insecure Design missing auth flows, IDOR
Threat-model before coding. List abuse cases, put rate limits on login and reset flows, and limit sensitive business actions. A scanner cannot find a design decision that was never made.
A05 Security Misconfiguration debug mode, default credentials
Expose only the {{actuator}} endpoints you need, switch off verbose errors, change default credentials, set security headers and review {{cors}}.
A06 Vulnerable and Outdated Components outdated dependencies
Run Dependency-Check or Trivy in CI and update on a schedule with Dependabot or Renovate. Log4Shell (CVE-2021-44228) is the standing example of one library putting thousands of applications at risk.
A07 Identification and Authentication Failures weak passwords, session issues
Enforce a real length rule (the report example later asks for 12 characters), throttle or lock after repeated failures, use Secure and HttpOnly session cookies, issue a new session ID at login, and offer MFA.
A08 Software and Data Integrity Failures insecure deserialization
Avoid native Java serialization of untrusted data, verify signatures on updates and build artifacts, and protect the CI pipeline that produces them.
A09 Security Logging and Monitoring Failures missing logs, exposed data
Log sign-ins, access denials and admin actions with a correlation ID, ship the logs to a {{siem}}, and never write secrets into them.
A10 Server-Side Request Forgery unvalidated URLs
Allow-list outbound hosts, resolve the name and block internal and link-local addresses (including the cloud metadata address 169.254.169.254), and disable redirects you do not need. See {{ssrf}}.

A secret is a string that grants power

Once a secret is committed, assume copies exist. A repository's {{git-history}} lives on every clone, in every CI cache and sometimes on every laptop.

Why scanners can find them

Two signals do most of the work. The first is shape: many providers give their keys a recognizable prefix and length, so a regular expression can match them. The second is randomness: a generated key looks nothing like English or a variable name, which shows up as high {{entropy}}. Entropy flags randomness, not secrecy. A short human-chosen password scores low and a hash or a UUID scores high, so treat the number as a clue and read the line.

Where secrets hide in Java projects

  • application.properties and application.yml, including profile files such as application-prod.yml.
  • Test resources, which often hold real credentials copied for convenience.
  • Dockerfile ENV lines, docker-compose.yml and CI variables printed in build logs.
  • Maven settings.xml, JDBC URLs that include a user and password, and Kubernetes Secret manifests. Base64 in a Secret is encoding, not encryption.
  • Old commits. The current file may be clean while the history is not.

The scanning tools

{{gitleaks}} is fast and reads git history. A baseline file lets you accept known findings so only new ones fail the build.

{{trufflehog}} scans deeper and can check whether a found credential is still valid. Recent releases ship as a standalone binary (for example brew install trufflehog), so check the project's install page if the pip package behaves differently.

Grep is crude and always available. It is good for a ten-minute first look and for confirming what a scanner reported.

When one is found, the order matters

  1. {{rotation}} first. Treat the secret as compromised. Issue a new one and revoke the old one before anything else, because deleting the commit does not delete the copies.
  2. Remove it from history. Rewrite the history with {{bfg}} or git filter-branch, force-push, and ask everyone to re-clone.
  3. Ignore the file. Add local config files such as application-local.yml to .gitignore.
  4. Read it from the environment. Spring resolves ${DB_PASSWORD} from environment variables, so the repository holds a name instead of a value.
  5. Move it to a {{secret-manager}}. AWS Secrets Manager and HashiCorp Vault add rotation, audit logs and short-lived credentials. The Infrastructure part shows Vault.

Penetration testing is controlled curiosity

A penetration test keeps asking one question: can someone with this starting access reach something they should not? The answer only counts if you were allowed to ask.

The phases

Each tab starts with the question that phase answers, then how to ask it, then the Java-side fix. Commands appear where the reference lists them. Run them only against systems you are authorized to test.

The question. What exists, and what is it running? You cannot test what you have not found. {{reconnaissance}} builds the list of hosts, services and technologies the other phases examine.

Passive

Never touches the target. Read DNS records, discover subdomains, and search {{certificate-transparency}} logs, where every issued TLS certificate is public.

Active

Sends traffic to the target, so it needs scope. {{port-scan}}ning finds open services, version detection names them, and {{fingerprinting}} identifies web technology.

Tools

Java angle
Version banners and default error pages often reveal the Tomcat or Spring version. An exposed {{actuator}} such as /actuator/env or /actuator/heapdump leaks configuration and memory.
Fix
Hide version banners, serve custom error pages, and keep actuator endpoints on an internal network or behind authentication.

The question. Does the application enforce who you are and what you may do, and does it treat every input as untrusted?

Authentication and authorization

  • Session analysis: timeout, Secure and HttpOnly cookie flags, {{session-fixation}} (does the ID change at login?), and concurrent sessions.
  • {{idor}}: ask for another user's record with your own session.
  • {{privilege-escalation}}: call administrator endpoints as a standard user.

The question. Does each API call carry proof of identity, and does it return and accept only what it should?

Tokens

A {{jwt}} is signed, not secret. Anyone can read its header and payload, and the signature only proves nobody changed them. Check that the server rejects the {{alg-none}} algorithm, never lets the token choose how it is verified, uses a strong signing key (weak HMAC secrets can be guessed offline), and validates expiry, issuer and audience.

Rate limits, data exposure and mass assignment

  • {{rate-limiting}}: send a bounded number of failed logins to a test account and see whether the service slows, locks or blocks. The reference loops 1,000 requests, which can disrupt a service by itself, so agree a limit in the rules of engagement first.
  • {{excessive-data-exposure}}: call /api/users/me and look for password hashes, internal IDs or personal data that the screen never shows.
  • {{mass-assignment}}: add a field such as isAdmin to a profile update and confirm the server ignores it.

The question. Once someone has a foothold, how far does it reach? This phase belongs to network engagements and needs explicit scope.

Security continues past the code

A flawless controller still runs in a container, in a cluster, in a cloud account, behind a pipeline. Each layer can undo the one inside it, so each layer needs its own controls.

A secret manager hands out credentials on demand. With {{dynamic-secrets}}, a Vault role creates a fresh database user for each request and deletes it when its {{ttl}} runs out, so a leaked credential expires on its own. In Kubernetes, the External Secrets Operator copies values from Vault into ordinary Secrets and refreshes them.

Security monitoring

Logs that nobody reads do not help. A {{siem}} collects them in one place so alerts and investigations can search across hosts. Filebeat ships the files to Elasticsearch in this example.

Anatomy of one finding

Every finding carries a location, a {{cwe}} identifier, a {{cvss}} score, the impact and the remediation. Edit the fields and the Markdown on the right follows. The checks beneath it test the rules a reviewer must follow: a precise location, a remediation, and a severity that matches the score.
