Java 8

Q1
Lambdas

Why must local variables used inside a lambda never change, while fields can be changed freely?

Short answer: a lambda gets a copy of a local variable's value, but a link to the object that holds a field. A copy can go out of date; a link cannot.

Why it happens: a local variable lives only while its method is running. It is stored in that method's private memory (the stack), which is thrown away when the method finishes. But a lambda can live longer than that: it can be saved in a field, returned, or run later on another thread. So when the lambda is created, Java copies the variable's current value into it.

If the variable could still change afterwards, the lambda would keep the old value while the method has a new one. One variable with two different values is a recipe for bugs, so the compiler simply forbids changing it. Java calls such a variable "effectively final".

Fields are different. They live inside an object in shared memory (the heap). The lambda keeps a link to that object (this) and reads the field through it every time. There is only one copy of the field, so nothing can go out of date. Making that field safe for several threads is still your job.

class Counter {
    private int total = 0;                 // a field: lives inside the object

    void run(List<Integer> xs) {
        int local = 0;                     // a local variable: lives only during run()
        xs.forEach(x -> total += x);       // OK: changes this.total through the link
        xs.forEach(x -> local += x);       // compile error: the lambda only has a copy of local

        // A workaround if you really need it: a one-item array (the array itself never changes)
        int[] sum = {0};
        xs.forEach(x -> sum[0] += x);
        // Better: let the stream add them up
        int s = xs.stream().mapToInt(Integer::intValue).sum();
    }
}
Q2
Lambdas

Comparator declares two methods, compare and equals. Is it still a functional interface?

Short answer: yes. Methods that every object already has from Object do not count.

Why it happens: a functional interface is an interface with exactly one method that you still have to fill in, so that a lambda can be that method. Every class automatically inherits equals(Object) from Object, so a lambda never needs to provide it. Comparator only lists equals again to attach documentation to it. Methods that already have a body, default and static methods, do not count either.

@FunctionalInterface
interface Rule {
    boolean check(Loan l);              // the one method a lambda fills in
    boolean equals(Object o);           // does not count: every object already has it
    String toString();                  // does not count
    default Rule and(Rule o) { return l -> check(l) && o.check(l); }   // has a body: does not count
}
Q3
Predicate

Why does Predicate.not exist when negate() already does the same thing?

Short answer: a method reference such as String::isBlank has no type until Java sees where it is used, so you cannot call negate() on it. Passing it into a static method gives it a type.

Why it happens: String::isBlank could become a Predicate<String>, a Function<String, Boolean>, or any other interface with the same shape. Java decides which one only by looking at where you put it. In String::isBlank.negate() there is no such place, so it does not compile. In not(String::isBlank), the method reference is a parameter of type Predicate, and that tells Java everything it needs.

lines.stream().filter(String::isBlank.negate());          // compile error
lines.stream().filter(s -> !s.isBlank());                  // works, but longer
lines.stream().filter(Predicate.not(String::isBlank));     // Java 11+

Predicate<String> blank = String::isBlank;                 // storing it in a variable also works
lines.stream().filter(blank.negate());
Q4
Predicate

p = a.and(b).or(c). For an item where a is true, b is false and c is true, which tests run, and what is the result?

Short answer: a, then b, then c. Three tests run, and the result is true.

Why it happens: chains are read from left to right, so p means (a && b) || c. and builds t -> a.test(t) && b.test(t), and or wraps that. Java's own && and || decide what runs:

  1. a is true, so && must also check b.
  2. b is false, so the whole and part is false.
  3. The left side of || is false, so c must be checked. It is true.

If a had been false, b would never have run. If the and part had been true, c would never have run.

Predicate<String> a = s -> { System.out.println("a"); return true;  };
Predicate<String> b = s -> { System.out.println("b"); return false; };
Predicate<String> c = s -> { System.out.println("c"); return true;  };

System.out.println(a.and(b).or(c).test("x"));   // prints a, b, c, true
System.out.println(a.and(b.or(c)).test("x"));   // prints a, b, c, true   -> this one means a && (b || c)
Q5
Predicate

Why does and call Objects.requireNonNull(other) immediately, instead of letting other.test crash later?

Short answer: so the error appears on the line that made the mistake, not somewhere else much later.

Why it happens: building a combined test and using it happen at different times, often in different places. Without the check, a.and(null) would quietly return a normal-looking test. It would only crash when used: maybe inside a stream, in another class, or on another thread. Worse, because and stops early, the null is only reached for items where a is true. If those are rare, the bug can stay hidden for weeks.

Predicate<Loan> eligible = active.and(rules.get("highRisk"));   // the map had no "highRisk" key: null
// With requireNonNull: NullPointerException HERE, on the line with the wrong rule name.
// Without it: a crash later, inside loans.stream().filter(eligible), and only for active loans.

negate() has no such check because it has no parameter to check.

Q6
Predicate

What does allMatch return on an empty stream, and why is that the logical answer?

Short answer: true. "Every item passes" can only be false if you can point at an item that fails, and an empty stream has none.

Why it happens: think of allMatch as searching for a failing item. If the search finds nothing, the answer is "no failures", which means true. The same reasoning gives anyMatch = false (nothing matching was found) and noneMatch = true (nothing matching was found).

This also explains the starting value when you combine many tests with and: you start from "always true", just as adding numbers starts from 0 and multiplying starts from 1.

List.<Loan>of().stream().allMatch(Loan::isActive);    // true
List.<Loan>of().stream().anyMatch(Loan::isActive);    // false
List.<Loan>of().stream().noneMatch(Loan::isActive);   // true

Predicate<Loan> all = List.<Predicate<Loan>>of().stream()
        .reduce(x -> true, Predicate::and);           // no rules at all: everything passes

A practical warning: if (loans.stream().allMatch(Loan::isApproved)) payOut(); pays out when the list is empty. Add !loans.isEmpty() when that matters.

Q7
Predicate

Why does isEqual check for null once, when the test is built, instead of using t -> Objects.equals(targetRef, t)?

Short answer: the value being compared against never changes, so checking it for null on every call would be wasted work. It also guarantees equals is never called on null.

Why it happens: a predicate is built once and then used many times. Anything that depends only on values known when it is built should be decided at that moment. It is the same idea as moving a calculation that never changes out of a loop.

// JDK version: decides ONCE which lambda to return
return (null == targetRef) ? Objects::isNull : object -> targetRef.equals(object);

// Simple version: checks targetRef == null again on every call
return t -> Objects.equals(targetRef, t);

Both give the same answers; the JDK version just does less work on each call. Note that it uses the target's own equals, so isEqual(new BigDecimal("3.5")) does not match 3.50, because BigDecimal.equals also compares the number of decimals.

Q8
Streams

Why does Stream.iterate(1, x -> x + 1).sorted().findFirst() never finish?

Short answer: sorted has to see every item before it can hand out the first one, and this source never ends.

Why it happens: most stream steps pass each item straight on (filter, map). That is why findFirst can usually stop early. sorted cannot: the smallest item might be the very last one, so it must collect everything first. With a source that never ends, it keeps collecting until the program runs out of memory. findFirst never gets a chance to stop anything, because no item ever reaches it.

Stream.iterate(1, x -> x + 1).limit(10).sorted().findFirst();       // fine: limit comes first
Stream.iterate(1, x -> x + 1).filter(x -> x % 7 == 0).findFirst();  // fine: nothing has to wait
Stream.iterate(1, x -> x + 1).sorted().findFirst();                 // never returns

distinct has a similar effect, and in parallel streams limit and skip become expensive for the same reason.

Q9
Streams

Why should you not use reduce to build a list?

Short answer: reduce is meant for combining values that never change, like adding numbers. Collecting items into a list is the job of collect.

Why it happens: reduce(start, combine) assumes combine makes a new value from two old ones, and that the start value can be reused safely. In a parallel stream, every worker begins from that same start value. If the start value is one ArrayList, all workers add to the same list at the same time: items get lost or duplicated, or the program crashes. Even on one thread, the "make a new list each time" version copies the list at every step, which is very slow.

collect was designed for this job: each worker gets its own fresh list, and the lists are joined at the end.

// Wrong: all parallel workers share one list
List<String> bad = names.parallelStream().reduce(new ArrayList<>(),
        (acc, n) -> { acc.add(n); return acc; },
        (l, r) -> { l.addAll(r); return l; });

// Right
List<String> good = names.parallelStream().collect(Collectors.toList());
List<String> same = names.parallelStream().collect(ArrayList::new, ArrayList::add, ArrayList::addAll);
Q10
Streams vs iterators

With filter(x -> x > 4).map(x -> x * 10).limit(2).toList() on [3, 8, 1, 12, 5, 9, 4, 15], how many numbers are read from the source, and how many times does the map lambda run?

Short answer: 4 numbers are read (3, 8, 1, 12), and map runs only twice (for 8 and 12).

Why it happens: a stream sends one item at a time through all the steps before it reads the next one. Follow the items:

  1. 3 fails the filter. 8 passes, becomes 80, and is the 1st item through limit.
  2. 1 fails the filter. 12 passes, becomes 120, and is the 2nd item through limit.
  3. limit(2) now has everything it needs, so it reports "I need no more". Before reading 5, the source asks whether anyone still wants items, hears no, and stops.

So 5, 9, 4 and 15 are never read at all. The Field Guide's "Streams vs iterators" simulation lets you step through exactly this.

List<Integer> r = Stream.of(3, 8, 1, 12, 5, 9, 4, 15)
        .peek(x -> System.out.println("read " + x))
        .filter(x -> x > 4)
        .map(x -> x * 10)
        .limit(2)
        .toList();
// read 3, read 8, read 1, read 12   ->  r = [80, 120]
Q11
Streams vs iterators

Add sorted() before limit(2). How many numbers are read now, and why?

Short answer: all 8. The result is [50, 80].

Why it happens: sorted cannot send the smallest value on until it has seen every value, because the smallest might come last. So it collects all the items, and only when the source is empty does it sort them and send them on. While it is collecting, nothing reaches limit, so limit never gets the chance to say "stop". The early stop is blocked by the sort.

Stream.of(3, 8, 1, 12, 5, 9, 4, 15)
        .peek(x -> System.out.println("read " + x))
        .filter(x -> x > 4)
        .map(x -> x * 10)
        .sorted()                 // collects 80, 120, 50, 90, 150, then sorts
        .limit(2)
        .toList();
// all 8 are read  ->  [50, 80]
Q12
Streams vs iterators

In a for-each loop over an ArrayList you call list.remove(x). Why does that throw ConcurrentModificationException, while it.remove() does not?

Short answer: the iterator checks that nobody changed the list behind its back. list.remove changes it behind its back; it.remove() changes it through the iterator, which keeps track.

Why it happens: an ArrayList keeps a counter of how many times it has been changed (modCount). When the iterator is created, it remembers that number. Every next() compares the two. list.remove(x) increases the list's counter without telling the iterator, so the next check fails and throws. it.remove() removes the item through the iterator, which updates both its position and the number it expects.

for (Loan l : loans) if (l.isClosed()) loans.remove(l);     // ConcurrentModificationException

for (Iterator<Loan> it = loans.iterator(); it.hasNext(); )  // OK
    if (it.next().isClosed()) it.remove();

loans.removeIf(Loan::isClosed);                             // Java 8: the same in one line

This check is best-effort: removing the second-to-last item often does not throw, because the loop ends before next() checks again. Do not rely on that.

Q13
Streams vs iterators

Why can a stream run in parallel, but an Iterator cannot?

Short answer: an iterator is one bookmark that only knows the next item, so there is nothing to split. A stream's source can split its remaining items in half and give one half to another worker.

Why it happens: an Iterator only offers hasNext() and next(). Two threads sharing one bookmark would just take turns, or step on each other. A stream's source is a Spliterator, which adds trySplit(): "give half of what is left to a new spliterator". For an ArrayList that is instant, since it just splits a range of positions. And because a stream controls its own loop, Java can decide which thread handles which part, then combine the results.

long sum = numbers.parallelStream()     // the list is split into chunks
        .mapToLong(Long::longValue)
        .sum();                         // each thread adds up its chunk, then the totals are added
Q14
Streams vs iterators

Your map lambda needs to call a method that throws IOException. Why is that awkward in a stream, but easy in a loop?

Short answer: a lambda passed to map is a Function, and Function.apply is not allowed to throw checked exceptions. In a loop, the code is your own method, which can simply declare throws IOException.

Why it happens: Java forces checked exceptions to be declared on every method they pass through. Your lambda is called by Java's stream code, and those methods were not written to pass on your IOException. So you have to catch it inside the lambda and wrap it in an unchecked exception, then unwrap it outside if you care.

// Stream: wrap and unwrap
try {
    List<String> texts = paths.stream()
        .map(p -> {
            try { return Files.readString(p); }
            catch (IOException e) { throw new UncheckedIOException(e); }
        })
        .toList();
} catch (UncheckedIOException e) {
    throw e.getCause();   // back to an IOException
}

// Loop: nothing special
List<String> texts = new ArrayList<>();
for (Path p : paths) texts.add(Files.readString(p));   // the method just says "throws IOException"
Q15
Optional

A method returns Optional<User>, but sometimes returns null. What happens to the caller?

Short answer: the caller gets a NullPointerException as soon as it calls anything on the result. That defeats the whole point of Optional.

Why it happens: Optional moves "there might be no value" from a nasty surprise into the return type. The caller trusts that type and writes findUser(id).map(...) without checking for null. If the method returns null instead of Optional.empty(), that call is made on null and crashes. The rule is simple: a method that returns Optional must never return null.

Optional<User> findUser(long id) {
    User u = repo.get(id);
    return u == null ? null : Optional.of(u);   // bug
    // return Optional.ofNullable(u);            // correct: empty Optional when u is null
}

String name = findUser(42).map(User::name).orElse("guest");   // crashes with the buggy version
Q16
java.time

Why can't you add Duration.ofDays(1) to a LocalDate?

Short answer: a Duration is an exact number of seconds, and a LocalDate has no time of day to add seconds to. Use plusDays(1) or a Period.

Why it happens: java.time keeps two kinds of "amount of time" apart. Stopwatch time (Duration) counts exact seconds. Calendar time (Period) counts days, months and years the way people do. A calendar day is not always 24 hours: on the days the clocks change, it has 23 or 25. So mixing the two could give wrong answers. A LocalDate only understands calendar units, so it refuses seconds and throws UnsupportedTemporalTypeException.

LocalDate d = LocalDate.of(2026, 3, 28);
d.plus(Duration.ofDays(1));   // UnsupportedTemporalTypeException: Unsupported unit: Seconds
d.plusDays(1);                // 2026-03-29
d.plus(Period.ofDays(1));     // 2026-03-29

// Where the difference shows: the night the clocks change in Amsterdam
ZonedDateTime t = ZonedDateTime.of(2026, 3, 28, 9, 0, 0, 0, ZoneId.of("Europe/Amsterdam"));
t.plusDays(1);                // 2026-03-29T09:00+02:00  (calendar: still 9 o'clock)
t.plus(Duration.ofDays(1));   // 2026-03-29T10:00+02:00  (stopwatch: exactly 24 hours later)
Q17
CompletableFuture

Inside a web request you call thenApply(heavyWork) on a future that has already finished. Which thread runs heavyWork?

Short answer: your own request thread, immediately, inside the thenApply call.

Why it happens: a step without Async in its name runs on whichever thread finishes the step before it. If that step is already finished when you attach the next one, no other thread is going to come along and run it. So the thread that called thenApply, your request thread, runs it right away. Only the methods ending in Async hand the work to a thread pool.

CompletableFuture<Rate> f = CompletableFuture.completedFuture(rate);   // already finished

f.thenApply(r -> {
    System.out.println(Thread.currentThread().getName());   // http-nio-8080-exec-3: the request thread
    return heavyWork(r);
});

f.thenApplyAsync(r -> heavyWork(r), cpuPool);               // runs on cpuPool instead

This is why an endpoint can be slow even though it "uses CompletableFuture": the work never actually moved to another thread.

Q18
Generics and erasure

Why can one ArrayList.class serve both List<String> and List<Loan>, but not List<int>?

Short answer: every object, whatever its class, is handled through a pointer, and all pointers use the same JVM instructions. An int is a raw number that needs different instructions.

Why it happens: after the compiler has checked your code, it removes the <String> or <Loan> part (type erasure). Inside, ArrayList keeps an Object[], and its compiled code uses pointer instructions such as aaload ("load a pointer from an array") and areturn ("return a pointer"). A pointer to a String and a pointer to a Loan look the same to the JVM, so the same code works for both.

An int is not a pointer. Loading one needs iaload, returning one needs ireturn, and long and double are even twice as big. One compiled class cannot use both kinds of instructions, so List<int> would need separate compiled code. Java's answer today is boxing (wrapping each int in an Integer object), or special classes like IntStream.

// Run javap -c on these two methods to see the different instructions
Object firstObj(Object[] a) { return a[0]; }   // aload_1, iconst_0, aaload, areturn
int    firstInt(int[] a)    { return a[0]; }   // aload_1, iconst_0, iaload, ireturn
Q19
Generics and erasure

Jackson can read JSON into a List<Loan> with new TypeReference<List<Loan>>(){}. If generics are erased, where does it find Loan?

Short answer: the {} creates a small anonymous subclass. The declaration of a class, including the type it extends, is kept in the class file and is not erased.

Why it happens: erasure removes type information from objects and instructions: a List<Loan> object at runtime is just an ArrayList. But declarations keep their full generic types in the class file, because other code needs them to compile against your class. A class declared as extends TypeReference<List<Loan>> is a declaration, so reflection can read List<Loan> back out of it.

abstract class TypeToken<T> {
    final Type type;
    protected TypeToken() {
        ParameterizedType sup = (ParameterizedType) getClass().getGenericSuperclass();
        this.type = sup.getActualTypeArguments()[0];   // read T from the subclass declaration
    }
}

Type t = new TypeToken<List<Loan>>() {}.type;
System.out.println(t);   // java.util.List<com.example.Loan>

new ArrayList<Loan>().getClass();   // class java.util.ArrayList   (no Loan: the object itself is erased)
Q20
Generics and erasure

Why does new T() fail, but passing a Supplier<T> works?

Short answer: while the program runs, T is just Object, so the JVM does not know which class to create. A Supplier<T> carries that knowledge as a value, from a caller who does know the real type.

Why it happens: new is compiled into an instruction that names one specific class. Inside a generic class there is no specific class to name, because one compiled class serves every T. The caller, however, writes Pool<StringBuilder> and knows exactly what it wants. So the caller passes a factory (such as StringBuilder::new), and the knowledge travels into your class as an object instead of as a type.

class Pool<T> {
    private final Supplier<T> factory;
    Pool(Supplier<T> factory) { this.factory = factory; }
    T borrow() { return factory.get(); }      // instead of new T()
}

var pool = new Pool<>(StringBuilder::new);   // the caller supplies the constructor

// The same idea with a Class object, for when you need reflection or arrays:
<T> T[] newArray(Class<T> type, int n) { return (T[]) Array.newInstance(type, n); }
Q21
Generics and erasure

In IntList.get, why check against size instead of relying on the array's own bounds check?

Short answer: the array is usually bigger than the list. Positions between size and the array's length exist in the array, but they are not part of the list.

Why it happens: a growable list keeps spare room so that add is usually fast: when the array is full, it creates one twice as big. So a list of 3 numbers may sit in an array of 10. The JVM's own check only knows the array's length (10), so reading position 5 would quietly return a leftover 0 instead of failing. ArrayList checks against size for exactly the same reason.

IntList list = new IntList(10);
list.add(7); list.add(42); list.add(3);   // size = 3, but the array has room for 10

// underneath: data = [7, 42, 3, 0, 0, 0, 0, 0, 0, 0]

list.get(5);   // with Objects.checkIndex(index, size): IndexOutOfBoundsException (correct)
               // without it: returns 0 (a silent bug)

Q22
Records

A record has a component List<String> tags. How do you make the record truly unchangeable?

Short answer: copy the list in the compact constructor: tags = List.copyOf(tags);.

Why it happens: a record's fields are final, but final only fixes which list the field points to, not what is inside that list. Without a copy, two things could still change the record:

  1. The caller keeps its own reference to the list it passed in, and adds to it later.
  2. Anyone who calls tags() gets the same list and can call add on it.

List.copyOf fixes both. It copies the items into a new list that cannot be changed, so the caller's list is no longer connected, and tags() returns a list that throws an error on add. It also refuses null items. If the list you pass in is already unchangeable (for example from List.of), it is reused without copying.

public record LoanTags(String loanId, List<String> tags) {
    public LoanTags {
        Objects.requireNonNull(loanId);
        tags = List.copyOf(tags);          // a copy that cannot be changed
    }
}

var source = new ArrayList<>(List.of("fixed"));
var t = new LoanTags("L1", source);
source.add("oops");                        // does not affect t
t.tags().add("oops");                      // UnsupportedOperationException

// Without the copy, both lines above would quietly change t,
// and its equals() and hashCode() would change too.

That last point is why this matters: records are often used as keys in a HashMap or items in a HashSet. If a record's contents change, its hashCode changes, and the map can no longer find the entry.

Q23
Sealed classes

Why is a default branch in a switch over a sealed type usually a bad idea?

Short answer: it switches off the compiler's "did you handle every case?" check. When someone adds a new subtype later, the default silently handles it, instead of giving a compile error at every switch that needs a decision.

Why it happens: the main benefit of a sealed type is that the compiler knows the complete list of subtypes. Because of that, it can confirm that a switch covers all of them, and warn you as soon as one is missing. A default branch means "anything else goes here", so the switch always counts as complete, whatever is added later. You have swapped a helpful compile error for behaviour you probably did not intend.

sealed interface Payment permits Card, Ideal, BankTransfer { }

BigDecimal fee(Payment p) {
    return switch (p) {
        case Card c         -> new BigDecimal("0.30");
        case Ideal i        -> new BigDecimal("0.29");
        case BankTransfer b -> BigDecimal.ZERO;
        // no default: adding "record Klarna(...) implements Payment" breaks
        // the build HERE, so nobody forgets to decide Klarna's fee
    };
}

BigDecimal feeWithDefault(Payment p) {
    return switch (p) {
        case Card c -> new BigDecimal("0.30");
        default     -> BigDecimal.ZERO;    // Klarna would now quietly be charged 0
    };
}

A default is still fine when you really mean "treat every other kind, including future ones, the same way". Make it a conscious choice, not a habit.

Java 21

Q24
Virtual threads

Your service has 8 CPU cores and only resizes images. Will virtual threads make it faster?

Short answer: no. Resizing is pure calculation, so 8 cores can resize 8 images at a time, however many threads exist.

Why it happens: virtual threads make waiting cheap. When a virtual thread waits for a database or another service, it steps off its carrier thread, and the carrier runs someone else in the meantime. Idle waiting time turns into useful work. Image resizing never waits: it keeps a CPU core busy from start to finish. There is no idle time to win back, so extra threads only add overhead.

A useful test: look at CPU usage under load. At 100%, you are limited by calculation and need more cores or faster code. At 20% while requests pile up, threads are waiting, and virtual threads (or a bigger pool) will help.

// Calculation-heavy: one thread per core is enough
ExecutorService cpu = Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());
images.forEach(img -> cpu.submit(() -> resize(img)));

// Waiting-heavy: one virtual thread per task is the right tool
try (var io = Executors.newVirtualThreadPerTaskExecutor()) {
    urls.forEach(u -> io.submit(() -> httpClient.send(get(u), ofString())));
}
Q25
Virtual threads

Why is Executors.newFixedThreadPool(200, Thread.ofVirtual().factory()) a bad sign?

Short answer: it puts virtual threads in a pool, which brings no benefit, and it quietly limits the work to 200 tasks at a time in a way that looks like a performance setting.

Why it happens: thread pools exist because classic threads are expensive to create (an operating-system thread and about 1 MB of memory each), so reusing them saves money. A virtual thread is a small Java object, cheaper to create than the pool's own bookkeeping. So the reason for having a pool disappears.

What is left is a side effect: at most 200 tasks run at once. If a limit is what you actually want, for example because a partner API allows only 10 calls at a time, say so directly with a Semaphore. That documents the reason, and limits only the scarce resource instead of all work.

// Unclear: is 200 a performance guess or a real limit?
var pool = Executors.newFixedThreadPool(200, Thread.ofVirtual().factory());

// Clear: cheap threads for everything, a hard limit only on the partner API
private final Semaphore partnerLimit = new Semaphore(10);

try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (String id : ids) {
        exec.submit(() -> {
            partnerLimit.acquire();
            try { return partnerApi.fetch(id); }
            finally { partnerLimit.release(); }
        });
    }
}
Q26
Pattern matching

A switch over a sealed interface was compiled when it covered every case. Later a new subtype is added, but only that subtype is recompiled. What happens when the switch receives the new type?

Short answer: the switch throws a MatchException.

Why it happens: the "every case is covered" check happens when compiling. But Java lets you recompile classes separately: a JAR built last month can run next to a class built today. So the compiler cannot be sure the list of subtypes is still the same when the program runs. To stay safe, it adds a hidden branch that throws if an unknown type ever arrives. (Before Java 21, a switch over an enum did something similar with IncompatibleClassChangeError.)

// Compiled when Payment only permitted Card and Ideal
String label(Payment p) {
    return switch (p) {
        case Card c  -> "card";
        case Ideal i -> "ideal";
        // the compiler secretly adds: default -> throw new MatchException(...)
    };
}
// Later Payment also permits Klarna and is recompiled, but this class is not.
label(new Klarna());   // java.lang.MatchException while the program runs

The fix is to rebuild everything. In practice this happens when a shared model JAR is upgraded, but a service that switches over its types is not rebuilt against the new version.

Threads and concurrency

Q27
Java Memory Model

A loop while (running) { ... } never stops, even after another thread sets running = false. Why does adding System.out.println inside the loop often seem to fix it?

Short answer: println uses a lock internally, which makes the thread re-read memory and stops the JIT compiler from reading running only once. It works by accident. The real fix is to make the field volatile.

Why it happens: unless something links the two threads (Java calls this a happens-before relationship), the JVM may assume no other thread changes running. The JIT compiler, Java's optimiser that runs while your program runs, sees that the loop never changes running. So it reads the field once and turns the loop into if (running) while (true) {...}. Even without that, a CPU core may keep using its own cached copy of the value.

System.out.println takes a lock inside PrintStream. Taking a lock forces fresh reads from memory, and the JIT cannot see through that call, so it stops making the "read once" shortcut. The loop happens to see the new value. But nothing in the Java rules promises this. A newer JVM, a different logger, or removing the debug line brings the bug straight back.

class Worker {
    private boolean running = true;              // bug: no visibility guarantee
    // private volatile boolean running = true;  // fix: every write is seen by later reads

    void stop() { running = false; }              // thread B
    void loop() {                                 // thread A
        long n = 0;
        while (running) { n++; }                  // may run forever without volatile
        System.out.println("stopped after " + n);
    }
}

// Also correct: an AtomicBoolean, or reading and writing it under the same lock.
private final AtomicBoolean running = new AtomicBoolean(true);

Rule of thumb: if a bug disappears when you add logging, you probably have a visibility bug.

Q28
Locks

Is a synchronized setter with a non-synchronized getter thread-safe?

Short answer: no. The getter never takes the lock, so nothing guarantees it sees the setter's change. It may return an old value. Both must use the same lock, or the field must be volatile.

Why it happens: a lock does two jobs. First, only one at a time: one thread runs the protected code while others wait. Second, visibility: when a thread releases a lock, the next thread that takes the same lock is guaranteed to see everything written before the release. That second promise only applies to threads that actually take the lock. A getter without synchronized never takes it, so it gets no promise.

For long and double it is even worse: without volatile, the JVM may write the 64 bits in two 32-bit halves, so a reader could see half of the old value and half of the new one.

class Rate {
    private BigDecimal value;

    public synchronized void set(BigDecimal v) { value = v; }
    public BigDecimal get() { return value; }                  // bug: may return an old value

    // Fix 1: the same lock on both sides
    public synchronized BigDecimal getSafe() { return value; }
}

// Fix 2, for one field that is simply replaced: volatile
class Rate2 {
    private volatile BigDecimal value;                   // safe, because BigDecimal never changes itself
    public void set(BigDecimal v) { value = v; }
    public BigDecimal get() { return value; }
}

volatile is enough here because each update is one single step: replacing the reference with a new object. As soon as an update reads and then writes (count++, or "check, then set"), you need a lock or an atomic class.

The JVM

Q29
From source to running code

Why does the first request to a freshly started Spring Boot app take much longer than the hundredth?

Short answer: warm-up. Classes are loaded the first time they are used, all code starts out slow (interpreted), and libraries set things up on first use. Later requests run fast compiled code with everything already in place.

Why it happens: the JVM does as little work as possible up front, and only optimises what turns out to be used a lot. The first request pays several one-time costs:

  1. Loading classes. Every class the request touches (Jackson serializers, Hibernate helpers, your DTOs) is found, read, checked and initialised the first time it is used.
  2. Interpreting. Code first runs in the interpreter, one instruction at a time, which is much slower than compiled code. Only methods that run often are compiled, first quickly by C1 and later thoroughly by C2.
  3. Lazy set-up in libraries. The first database call may open connections, Hibernate prepares its queries, Jackson builds a serializer per type, and Spring MVC works out which controller handles which URL.
  4. Empty caches. CPU caches, the JIT's usage statistics and your own application caches all start empty.
# See which classes load during the first request
java -Xlog:class+load:file=classes.log -jar app.jar
# Watch methods being compiled as traffic comes in
java -XX:+PrintCompilation -jar app.jar

Ways to reduce it:

  • Send some warm-up traffic before the pod is marked ready.
  • Use Class Data Sharing (CDS), which loads pre-processed classes from an archive. Spring Boot 3.3+ can create one for you.
  • Open database connections at start-up (Hikari's minimum-idle setting).
  • For instant start-up, GraalVM native image or CRaC, at the cost of a more complex build or less runtime optimisation.
Q30
Garbage collection

Heap usage climbs steadily, then a full garbage collection brings it back down to the same level each time. Is that a memory leak?

Short answer: no. That saw-tooth shape is normal: garbage builds up until the collector runs. A leak looks different: the level the heap drops back to after each full collection keeps rising over time.

Why it happens: the garbage collector does not free an object the moment it stops being used. It lets garbage pile up and cleans it in batches, because that is much cheaper per object. So the heap always grows between collections. The number that matters is what is left after a full collection: everything that is still reachable. If that stays flat, nothing is piling up. If it grows with every cycle, something is holding on to objects it should have let go, which is exactly what a memory leak in Java is.

How to check:

# A GC log: compare the heap size after each collection over a few hours
java -Xlog:gc*:file=gc.log:time,uptime -jar app.jar

# Quick object counts per class, without a full dump. Take two a few minutes apart and compare.
jcmd <pid> GC.class_histogram | head -20

# A full heap dump; open it in Eclipse MAT and look at the "dominator tree"
jcmd <pid> GC.heap_dump /tmp/heap.hprof

Common causes when the level does rise: a static map that things are added to but never removed from, ThreadLocal values that are never removed on pooled threads, listeners that are registered but never unregistered, and caches without a size limit.

Spring Boot

Q31
Transactions and proxies

Two @Transactional methods are in the same class. One calls the other, which is marked REQUIRES_NEW. Does the inner method get its own transaction?

Short answer: no. A call inside the same class goes through this, not through Spring's proxy, so the inner annotation is never seen. The inner method simply runs inside the outer transaction.

Why it happens: @Transactional is not handled by the Java compiler or the JVM. Spring makes it work by wrapping your bean in a proxy: a generated stand-in object. When another bean calls an annotated method, the call reaches the proxy first. The proxy starts the transaction, calls your real method, then saves (commits) or undoes (rolls back). Other beans always receive the proxy when they inject your class, so their calls go through it.

Inside your own class, though, this is your real object, not the proxy. this.audit() is a plain Java method call straight to your code. The proxy, the only thing that knows what REQUIRES_NEW means, is never involved.

@Service
public class LoanService {

    @Transactional
    public void approve(long id) {
        loanRepo.markApproved(id);
        audit(id, "APPROVED");               // really this.audit(): skips the proxy
        throw new IllegalStateException();   // undoes the approval AND the audit row
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)   // ignored for the call above
    public void audit(long id, String event) {
        auditRepo.save(new AuditEntry(id, event));
    }
}

You can confirm it while debugging: TransactionSynchronizationManager.getCurrentTransactionName() prints the same name in both methods.

The fix is to make the call go through a proxy, which means the method has to live in another bean:

@Service
class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record(long id, String event) {
        auditRepo.save(new AuditEntry(id, event));
    }
}

@Service
class LoanService {
    private final AuditService audit;                 // Spring injects the PROXY
    LoanService(AuditService audit) { this.audit = audit; }

    @Transactional
    public void approve(long id) {
        loanRepo.markApproved(id);
        audit.record(id, "APPROVED");        // goes through the proxy: its own transaction, saved at once
        throw new IllegalStateException();   // the approval is undone; the audit row stays
    }
}

The same one mechanism explains a whole family of surprises:

  • @Async, @Cacheable, @Retryable and @PreAuthorize also do nothing when a method calls another method of the same class.
  • These annotations are ignored on private and final methods, because a generated subclass cannot override them.
  • Code in @PostConstruct runs before the proxy exists, so @Transactional has no effect there.

One more detail: REQUIRES_NEW pauses the outer transaction and takes a second database connection from the pool. If many requests do this at once with a small pool (Hikari's default is 10), they can each hold one connection while waiting for a second, and the pool runs dry.
