    The only two things a computer can do with memory

    Think of the computer's memory as a very long street of houses, each with a house number. To reach a house, the computer has exactly two options:

    Jump. If it can work out the house number, it goes straight there. One step, no matter how long the street is.

    Walk. If it doesn't know the number, it has to start somewhere and go door to door, one step per house.

    That's the whole game. Every data structure in this guide is a different way of arranging the houses so you can jump more and walk less. Try it below on a row of 12 numbers. Each box shows its value and its "house number" (address).

    Pick a position, then jump or walk.

    Jumping works here because the boxes sit side by side and each one is the same size (4 bytes). So box number i is always at start + i × 4. One small sum, and you're there. Keep this in mind — it is the reason arrays are fast, and the reason some other structures are not.

    Measuring speed

    How we talk about "fast" and "slow"

    We don't measure algorithms in seconds, because seconds depend on the machine. Instead we ask: if the input gets 10 times bigger, how much more work is there? That's what Big-O notation describes. The letter n just means "how many items you have".

    Written asNicknameEveryday pictureFor 1 million items
    O(1)InstantOpening a book at a bookmark. Doesn't matter how thick the book is.1 step
    O(log n)HalvingFinding a word in a dictionary by opening the middle and throwing away the wrong half, again and again.~20 steps
    O(n)One look eachReading every name on a class list once.1 million
    O(n log n)Sorting speedSorting a deck of cards the smart way. A bit more than one look each.~20 million
    O(n²)Every pairEveryone at a party shaking hands with everyone else.1 trillion
    O(2ⁿ)Every groupTrying every possible combination of toppings on a pizza. Each new topping doubles the options.impossible
    O(n!)Every orderTrying every possible seating order at a dinner table.impossible

    Big-O ignores small details like "3 steps per item instead of 2", because when n is huge, the shape of the growth is what decides whether your program finishes.

    Four things that confuse almost everyone

    Where does "log" come from? log n is simply "how many times can I cut n in half before I reach 1?" 1,000 → 500 → 250 → … about 10 cuts. A billion needs only about 30. Whenever an algorithm throws away half of what's left at each step, you get log n.

    Two loops aren't always n². If the inner loop keeps going from where it stopped last time (instead of restarting), the total work is still about 2n. Count the total number of steps over the whole run, not "per loop".

    "Fast on average". Java's ArrayList sometimes has to copy everything into a bigger array when it fills up. That one add is slow, but it happens so rarely that, spread over all adds, each one is still instant. This is called amortized cost.

    Memory counts too. Besides time, we measure extra memory used. A function that calls itself (recursion) uses memory for every call that hasn't finished yet. In Java, around 10,000–100,000 unfinished calls will crash with StackOverflowError.

    The big idea

    Slow code is always doing one of six silly things

    The first solution you think of (often called "brute force") is usually correct but slow. It's slow because it keeps repeating some work. There are only six kinds of repeated work, and every technique in this guide fixes one of them. When you're stuck, write the slow version, then ask: which of these six is it doing? The answer tells you which tool to use.

    Calculating the same thing again and again

    Like adding up your receipts from scratch every time someone asks "how much did we spend so far?"

    Fix: write the answer down and reuse it. (Running totals, memoization, dynamic programming)

    Looking through everything to find one thing

    Like scrolling through your entire phone to find one contact, instead of typing the name.

    Fix: give each item a labelled spot so you can go straight to it. (Hash maps, hash sets, counting arrays)

    Searching through a messy pile

    Like looking for a word in a dictionary whose pages are shuffled.

    Fix: put things in order once, then keep cutting the search in half. (Sorting, binary search, TreeMap)

    Starting over when almost nothing changed

    Like recounting all the people on a train every time one person gets on.

    Fix: just adjust for what came in and what went out. (Two pointers, sliding window)

    Keeping options that have already lost

    Like a talent show still considering contestants who were clearly beaten.

    Fix: throw them out the moment they can't win. (Monotonic stack, monotonic deque, heap, greedy)

    Walking down roads you know are dead ends

    Like exploring a maze without chalk, so you keep visiting the same corridors.

    Fix: turn back early, and mark where you've been. (Backtracking with pruning, visited sets, union-find)

    Method

    How to solve a problem you've never seen

    Follow these steps in order, and say them out loud in an interview. Interviewers care about how you think as much as the final code.

    1. Say the problem back in your own words. What goes in, what comes out? Then ask questions: Is the input sorted? Can there be repeats? Negative numbers? An empty input? What should I return if there is no answer?
    2. Solve a tiny example with pen and paper. Five items is enough. Watch what your own hands do — the algorithm is often hiding there.
    3. Look at the input size. Use the "input size as a hint" table to know how fast your answer must be before you design anything.
    4. Write the simple, slow solution first, and say how slow it is. It proves you understand the problem and gives you something to improve.
    5. Find the repeated work. Which of the six silly things is the slow version doing?
    6. Pick the tool and say the rule it keeps. For example: "My window never contains a repeated letter." That rule is why your answer is correct.
    7. Walk through your example by hand before coding. Write down the variables after each step. Finding a mistake here takes seconds.
    8. Write simple code. Clear names, small helper methods, no clever tricks you can't explain.
    9. Test the awkward cases. Empty input, one item, all items the same, all negative, the largest allowed input, numbers too big for int.
    10. State time and memory use, then mention one variation. For example: "If the input were already sorted, I could use two pointers and skip the hash map."

    When you get a problem wrong, find out why

    "I failed" teaches nothing. Pick the real reason from this list:

    What went wrongWhat to do
    I misunderstood the questionSlow down on step 1. Write the expected output of the example before anything else.
    I didn't know the data structureReread that chapter and build the structure yourself from scratch once.
    I didn't see which tool to useAdd the problem's clue to your own notes. Do two more problems of that type.
    My code had a bugRewrite it from a blank file without looking. Use a debugger only after that.
    I forgot an awkward caseAdd it to a personal checklist you go through at step 9.
    I got the speed wrongRecount: total steps over the whole run, not steps per loop.

    Then solve one easier problem of the same type, and come back to the original three days later.

    How to make it stick

    Solving a problem once doesn't mean you've learned it. After you first solve it, solve it again from an empty file on day 1, day 3, day 7 and day 21. If you can't, start the count again. Re-solving four old problems teaches more than reading four new solutions.

    Build these yourself

    Writing a structure from scratch is the fastest way to truly understand it. Tick them off as you finish.

      How you'll know you're ready

      Interview-ready: you solve easy problems in 10–15 minutes and medium ones in 25–35, you say how fast your solution is, you handle the awkward cases, and you can explain why you chose your approach.

      Mastery: you see a brand-new problem and work out the approach by spotting the repeated work; you can explain why your answer is always correct; and you could teach any chapter here to a friend on a whiteboard.

      What matters isn't how many problems you've solved. It's how many you can solve that you've never seen before.
